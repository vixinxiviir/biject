# Spec: document the public API — the command half, and turn the lint on

**Target release:** 0.9
**Repository:** `bijection` (free crate)
**Depends on:** 0.9d, which must be finished, because this spec ends by making
an undocumented public item a compile error across the whole crate.
**Size:** roughly seventy doc comments across four files, one lint attribute,
and one user-visible fix that falls out of the work.

---

## 1. The gap

0.9d documented the database half. This is the rest: the comparison, the row
diff, and the command surface. Then `#![deny(missing_docs)]` goes on, so the
crate cannot regress.

There is also a plain defect hiding in here. Today:

```
$ biject --help
A CLI tool for diffing data and schemas

Usage: biject <COMMAND>

Commands:
  schema
  data
  batch
  help    Print this message or the help of the given subcommand(s)
```

Three commands with nothing beside them. Anybody's first contact with this tool
is a list of three words. Fixing that is not a separate task — in clap's derive
API a doc comment on a variant *is* its help text, so documenting `Commands`
fixes `--help` as a direct consequence.

## 2. Scope

- `src/lib.rs` — the crate-level doc comment, which does not exist.
- `src/schema.rs`
- `src/data.rs`
- `src/cli.rs`
- Anything 0.9d left behind, if the count in section 6 says so.

One known defect to fix while you are in there. `run_schema_diff_frames_with_catalog`
in `src/schema.rs` carries two doc comment blocks stacked on top of each other,
and the first one — "Returns structured schema diff data from pre-loaded
DataFrames. Used by the GUI when sources are SQL Server or other connectors." —
describes a different function. It belongs to `run_schema_diff_frames` or was
left behind by a rename. Work out which from the code, move or delete it, and
say which you did and why.

Read section 3 of 0.9d before starting. Its rules on style, and its rule about
not inventing a description for something you cannot work out, apply here
unchanged and are not repeated.

## 3. The crate-level doc comment

`src/lib.rs` is seven `pub mod` lines. It is the landing page on docs.rs.

Write a `//!` header that says, in a short paragraph each:

- **What the crate does** — compares two datasets or two schemas across CSV,
  PostgreSQL, MySQL, SQL Server and SQLite, and reports what differs.
- **The two comparisons and where they live**: `schema` for structure, `data`
  for rows, `catalog` for what the database itself declares.
- **The one thing an embedder has to understand**: a comparison can be partial,
  and the result says so. Point at `CatalogAvailability` and
  `TableCatalog::unread` by name. Somebody reading `changes.is_empty()` as "the
  schemas match" is the single most likely misuse of this library, and this is
  the place to head it off.

Add a one-line `//!` header to each `pub mod` line that lacks one, or to the
module file where that reads better. Do not duplicate a header a module already
has.

## 4. `src/cli.rs`, and how clap changes what a doc comment means

This file is different from the others: here a doc comment is not only
documentation, it is program output. In clap's derive API a `///` on a variant
or field becomes its help text — **unless** an explicit `help = "..."` attribute
is present, which wins.

So:

**Variants of `Commands`** have no `about` today. A doc comment on each gives
`biject --help` the descriptions it is missing. Write one line each, phrased as
help text rather than as prose about the code:

- `Schema` — compare the structure of two tables or files.
- `Data` — compare the rows of two tables or files, matched on a key.
- `Batch` — run many data comparisons from a manifest.

Use your own wording; those are the meanings, not the strings.

**Fields that already carry `help = "..."`** keep it. Add a `///` only if there
is something to say to a reader of the source that does not belong in `--help`,
and expect that to be rare. Do not move a `help` attribute into a doc comment,
and do not delete one: the two are not interchangeable, because a doc comment
also has to make sense on docs.rs.

**Fields with no `help` attribute** — `source`, `target`, `key`, `output`,
`format`, `temp` and their siblings — currently appear in `--help` with no
description. A doc comment fixes that, and **that is a user-visible change**.
Make it deliberately: write help text a user needs, not a note to a maintainer.
`temp` in particular is opaque from its name alone; if you cannot tell what it
does from `data::validate_export_args` and its call site, that is a case for the
rule about not inventing one.

`dispatch` and `Cli` are already documented. Leave them.

### Show the change

`--help` output is part of this diff even though it appears in no file. Paste
the full `biject --help`, and `biject schema --help`, before and after.

## 5. Turning the lint on

Once the count in section 6 reaches zero, add to `src/lib.rs`:

```rust
#![deny(missing_docs)]
```

`deny`, not `warn`. A warning in a crate this size is a warning nobody sees.

This must be the **last** thing you do, and the build must be clean immediately
after. If it is not, the count was wrong somewhere — fix the documentation, do
not weaken the attribute, do not add `#[allow(missing_docs)]` to a module, and
do not add `#[doc(hidden)]` to make an item disappear from the lint.

If some item genuinely cannot be documented without knowing something you do not
know, then this final step does not land in your change. Do everything else,
leave the attribute out, and say in your report exactly which items blocked it.
An honest incomplete result is the correct outcome there; a `#[allow]` that
hides one item and silently exempts every future item added beside it is not.

Expected files: `src/lib.rs`, `src/schema.rs`, `src/data.rs`, `src/cli.rs`, and
any file section 6's count sent you back to. Every changed line should be a doc
comment, a blank line, or the single lint attribute.

## 7. Non-goals

- **No behaviour changes**, with the one named exception: `--help` gains
  descriptions, because in clap that is what documenting the type does. Nothing
  about parsing, defaults, validation or output changes.
- **No renames, no signature changes, no visibility changes.** 0.9f.
- **Do not add a flag, remove one, or change one's `help` text** beyond adding
  descriptions where there are none.
- **Do not touch `src/connectors/`, `tauri-app/`, `README.md` or `CHANGELOG.md`.**
- **No new dependencies.**
