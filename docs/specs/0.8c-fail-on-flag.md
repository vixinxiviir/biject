# Spec: `--fail-on` for gating CI without a policy file

**Target release:** 0.8
**Repository:** `bijection` (free crate)
**Depends on:** nothing. Can be done at any time, in any order.
**Size:** one flag, one enum, one branch, tests. The smallest spec in the
backlog — a good one to take first if you have not worked in this repository
before.

---

## 1. The gap

To make CI fail when a schema changes incompatibly, you must write a JSON policy
file containing exactly one line:

```json
{ "fail_on_breaking": true }
```

Then commit it, and point `--policy` at it. That is a file, a path and a concept
to learn, for the single most common thing anyone wants from this tool in CI.

`biject schema` currently exits 0 whatever it finds, unless a policy says
otherwise. So the obvious pipeline step silently passes on a breaking change:

```bash
biject schema --source "$PROD" --source-query orders --target "$STAGING" --target-query orders
```

## 2. What to build

### 2.1 The flag

On the `Schema` command in `src/cli.rs`:

```rust
#[arg(
    long,
    value_enum,
    help = "Exit non-zero when the comparison finds changes at or above this severity"
)]
fail_on: Option<FailOn>,
```

```rust
/// How much of a difference is enough to fail the command.
#[derive(Clone, Copy, Debug, ValueEnum)]
#[value(rename_all = "kebab-case")]
pub enum FailOn {
    /// Any change at all, including ones that are safe for readers.
    Any,
    /// Changes classified as breaking. The useful default for CI.
    Breaking,
}
```

Put `FailOn` wherever `ExportFormat` lives so the CLI's value enums stay
together.

### 2.2 What each level means

Decide from the `SchemaDiffResult` that already exists. Do not recompute
anything.

**`breaking`** — fail when `!compatibility.backward_compatible`. That is the
existing verdict, which already accounts for removed columns, unsafe type
changes, dropped `NOT NULL`, and constraints the target no longer enforces.
Reusing it is the point: `--fail-on breaking` must agree with what the report
printed, always. Two definitions of "breaking" that could drift is a bug waiting
to happen.

**`any`** — fail when the comparison found anything: `added`, `removed`,
`type_changes` or `metadata.changes` is non-empty.

Rename suggestions do not count on their own. A rename is a guess about a
column that is already reported as one added and one removed, so it is never
the only finding.

### 2.3 The gap that must not pass silently

`--fail-on` asks whether the schemas differ. If the comparison could not see
part of the schema, it does not know.

**When `--fail-on` is given and `metadata.is_complete()` is false, say so on
stderr**, whatever the outcome:

```
warning: --fail-on judged this on an incomplete comparison. Schema metadata was
not compared: source: file sources have no catalog to read. Declared types,
nullability, defaults and constraints were not part of this result.
```

Use the reasons from `metadata.gaps()`. Do the same when
`metadata.unread_constraints()` is non-empty, naming the kinds.

Do **not** fail the command because of it. Comparing two CSVs is a legitimate
use with no catalog to read, and failing there would make the flag useless for
files. The requirement is that it never reports a clean pass while quietly
having skipped a whole category — the person reading the CI log has to be able
to see what the green tick covered.

### 2.4 How it fails

Reuse the existing error path so behaviour matches `--policy`:
`schema_diff` returns `Err`, `main.rs` prints it and exits 1.

Add a variant to `SchemaDiffError`. Message:

```
schema comparison failed --fail-on breaking: the target is not backward compatible with the source
```

```
schema comparison failed --fail-on any: 3 change(s) found
```

The check runs **after** the report is rendered and after `--output` is written.
Someone whose build just failed needs the comparison, and a file they asked for
must not go missing because the command exited non-zero.

### 2.5 With `--policy`

Both may be given. The policy is evaluated first, exactly as now; if it fails,
that error wins and `--fail-on` never runs. They are independent, and neither
implies the other.

## 3. Non-goals

- **No new severity levels.** Two, no more.
- **Do not change the compatibility calculation**, or add a second definition of
  "breaking" anywhere.
- **Do not change exit codes for anything else.**
- **Do not touch `src/connectors/` or the `data` command.**
- **No new dependencies.**

## 5. Tests

In `src/schema.rs`'s test module, using the existing helpers for building a
`SchemaDiffResult`.

| Test name | Must assert |
| --- | --- |
| `fail_on_breaking_agrees_with_the_verdict_the_report_printed` | A result with `backward_compatible: false` fails; one with `true` passes. Comment: two definitions of breaking would drift |
| `fail_on_any_catches_a_change_that_is_safe_for_readers` | A result with one added column and `backward_compatible: true` passes under `breaking` and fails under `any` |
| `identical_schemas_pass_at_every_level` | An empty result passes under both |
| `a_rename_suggestion_alone_does_not_fail_anything` | A result whose only content is a rename suggestion passes under `any`. Comment: the underlying add and drop are what get reported |
| `without_the_flag_nothing_fails` | The same failing result exits successfully when `fail_on` is `None` |
| `an_incomplete_comparison_is_announced_before_it_is_judged` | With `fail_on` set and `metadata.is_complete()` false, the warning text is produced and contains the reason from `gaps()`. Assert the command still returns the verdict rather than erroring on the gap |
| `a_constraint_kind_that_was_not_read_is_named_in_the_warning` | With `unread_constraints()` non-empty, the warning names the kind |
| `a_policy_failure_takes_precedence` | Both `--policy` (failing) and `--fail-on` set: the error is the policy's |

For the warning, factor the text into a function returning `Option<String>` so a
test can assert on it without capturing stderr. Print it at the call site.

### Demonstrate the exit codes

Build two SQLite tables where the target drops a column, then run each of these
and report the command, the exit code and the last line of output:

```bash
cargo run -- schema --source sqlite://x.sqlite --source-query a --target sqlite://x.sqlite --target-query b; echo "exit=$?"
```

```bash
cargo run -- schema --source sqlite://x.sqlite --source-query a --target sqlite://x.sqlite --target-query b --fail-on breaking; echo "exit=$?"
```

The first must be 0 and the second 1, with the same comparison printed above
both.
