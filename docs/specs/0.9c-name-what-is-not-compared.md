# Spec: name what the comparison does not look at

**Target release:** 0.9
**Repository:** `bijection` (free crate)
**Depends on:** 0.9a and 0.9b, because the list this produces is wrong until
foreign keys are read. Everything else in it is independent.
**Size:** one list, one renderer, three call sites, tests. Small, and the most
direct expression of what this project is for.

---

## 1. The gap

Run `biject schema` against two PostgreSQL tables and get:

```
No schema differences found.
```

The reader concludes the two tables are the same. They may not be. The tool has
not looked at triggers, generated-column expressions, collations, identity and
sequence settings, comments, partitioning, storage parameters, or grants. Any
one of those can differ and change what the table does.

Every existing honesty mechanism in this codebase answers a *runtime* question —
`CatalogAvailability` says a catalog was unreadable, `unread` says a kind was not
retrievable from this engine. Neither says the thing that is true on every run
of every engine: **there are parts of a schema this tool has never examined and
never will report on.**

That is a permanent, static fact about the tool, and it currently appears
nowhere: not in the report, not in the JSON, not in the README.

---

## 2. What to build

### 2.1 The list

In `src/schema.rs`, a module-level constant naming what a schema comparison
covers and what it does not.

```rust
/// Parts of a schema this tool does not examine.
///
/// Static, not a runtime finding. `CatalogAvailability` reports a catalog that
/// could not be read and `TableCatalog::unread` reports a kind this engine
/// would not give up; both are about a particular run. This is about the tool:
/// these are never compared, on any engine, however well the catalog reads.
///
/// Printed with every comparison, because "no differences found" and "no
/// differences among the things I looked at" are different statements and the
/// reader cannot tell them apart otherwise.
const NOT_COMPARED: &[&str] = &[
    "triggers",
    "views and materialised views",
    "generated and computed column expressions",
    "identity, sequence and auto-increment settings",
    "collations and character sets",
    "table and column comments",
    "partitioning",
    "storage parameters, tablespaces and fill factors",
    "grants and row-level security policies",
    "anything in a table other than the one named",
];
```

Each entry must be something the tool genuinely does not read. **Check each one
against the connectors before you commit it.** An entry that is actually
compared is worse than no list at all: it teaches the reader to distrust the
part that is true.

That last entry earns its place because it is the one people assume. `biject
schema` compares two tables. A foreign key names another table and the reference
is recorded, but nothing is read from the far side and nothing is checked about
it.

### 2.2 The list that must not go stale

The counterpart is what *is* compared, and it must be impossible to add a
constraint kind without this list noticing.

```rust
/// What a schema comparison does examine.
fn compared() -> Vec<String>
```

It returns the fixed column-level items — column names, declared types,
nullability, defaults, ordinal position — followed by one entry per
`ConstraintKind::ALL`, using each kind's `Display`.

Deriving the constraint half from `ConstraintKind::ALL` rather than typing it
out is the point. When a later release adds a kind, the list grows with it and
nobody has to remember. Section 4 has the test that enforces this.

### 2.3 Where it appears

**Text report.** After the findings and after any existing gap and unread
sections, so it reads as a footer rather than a warning:

```
Not compared: triggers, views and materialised views, generated and computed
column expressions, identity, sequence and auto-increment settings, collations
and character sets, table and column comments, partitioning, storage parameters,
tablespaces and fill factors, grants and row-level security policies, anything
in a table other than the one named.
```

Wrap it the way the rest of the report wraps text. Do not colour it as an error
or a warning — it is not one; it is the scope of a result that may be perfectly
clean.

It prints on **every** schema comparison, including one that found differences
and one where no catalog was available at all. A run against two CSV files still
prints it, because the reader of that run needs it most.

**JSON export and `--json`.** A new top-level object:

```json
"scope": {
  "compared": ["column names", "declared types", "..."],
  "not_compared": ["triggers", "..."]
}
```

`SchemaDiffResult` is already `#[non_exhaustive]`, so adding a field is not a
break for embedders.

**CSV export.** No change to the file. Its rows are a change list with a fixed
header (`category,subject,detail,from,to,breaking`) and interleaving prose would
corrupt something meant to be loaded by another program.

Instead, when `--format csv` is used, **print the same footer to stderr.** The
file stays machine-readable and the person who ran the command still sees the
scope. Say that in a comment, because deleting a stderr write that has no
matching assertion in the file is an easy thing for someone to tidy away later.

### 2.4 Foreign keys in the policy

Small, and it belongs here rather than in 0.9a or 0.9b: `require_constraints`
accepts `primary_key`, `unique`, `check` and `index`, validated in two places in
`src/schema.rs` — a match that rejects unknown names with a message listing the
valid ones, and a second match that maps a name to a `ConstraintKind`.

Add `foreign_key` to both, and to the error message.

Note that the second match ends with `_ => continue`, which means a name that
gets past the first check is silently ignored. Leave that structure alone; just
make sure the two lists agree. If you can make them share one function without
restructuring anything else, do — but do not turn this into a refactor.

## 3. Non-goals

- **No flag to suppress the footer.** Somebody will ask. The answer is no, for
  the same reason there is no flag to suppress the compatibility verdict: the
  scope is part of the result, not decoration on it.
- **Do not make the list engine-specific.** "PostgreSQL exclusion constraints"
  is true and belongs in a later release with a per-engine mechanism behind it.
  A list that is right for every engine is worth more now than one that is
  precise for one.
- **Do not add anything to `TableCatalog` or `CatalogAvailability`.** Those model
  what happened on a run. This is about what the tool is.
- **Do not touch `src/connectors/`, `src/data.rs` or `tauri-app/`.**
- **No new dependencies.**

## 4. Tests

In `src/schema.rs`'s test module.

| Test name | Must assert |
| --- | --- |
| `every_constraint_kind_appears_in_what_the_report_claims_to_compare` | For each `ConstraintKind::ALL`, its `Display` appears in `compared()`. **This is the test that keeps the list honest — write it first** |
| `a_clean_comparison_still_says_what_it_did_not_look_at` | A result with no differences renders the footer |
| `a_comparison_with_no_catalog_at_all_still_says_it` | A result whose metadata is `NotADatabase` on both sides renders the footer |
| `the_footer_is_separate_from_the_reasons_metadata_was_unavailable` | A result with both a gap and the footer produces both, and the footer text does not appear inside the gap section |
| `the_json_result_carries_both_halves_of_the_scope` | Serialised JSON has `scope.compared` and `scope.not_compared`, both non-empty |
| `the_csv_export_is_unchanged_by_this` | The CSV bytes for a given result are exactly what they were: same header, same row count |
| `foreign_key_is_a_valid_constraint_kind_in_a_policy` | A policy with `"require_constraints": ["foreign_key"]` validates, and one with `"reference"` is rejected with a message naming the five valid kinds |

## 5. Documentation

`README.md` documents the `schema` command. Add a short subsection under it
stating what a schema comparison covers and what it does not, with the same
list. Two short paragraphs; do not reproduce this spec.

This is one of the few specs permitted to edit `README.md`.

```bash
cargo run -- schema --source source.csv --target target.csv
```

Paste the whole output. Two identical CSVs is the case this spec exists for: the
report says nothing differs, and must now also say how much of a schema it was
in a position to check.
