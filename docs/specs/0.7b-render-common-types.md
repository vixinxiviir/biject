# Spec: rendering a canonical type — numbers, strings, booleans

**Target release:** 0.7
**Repository:** `bijection` (free crate)
**Depends on:** `0.7a-dialect-and-identifier-quoting` (the `Dialect` enum) and the
canonical type model already in `src/sqltype.rs`
**Size:** one function plus a lookup, added to `src/sqldialect.rs`

This is the first of two rendering specs. This one covers numbers, strings and
booleans. `0.7c` covers dates, times, binary and structured types, which is
where most of the refusals live. Do not implement 0.7c's types here — a
canonical type this spec does not list must return `Err`, and 0.7c will fill
them in.

---

## 1. Why

`src/sqltype.rs` can reduce `CHARACTER VARYING(50)` to a canonical
`varchar` with parameter `50`. Nothing can turn it back into text that a
particular engine accepts. Migration generation needs exactly that: to write a
column definition for MySQL, it has to know MySQL spells an unbounded string
`LONGTEXT` and PostgreSQL spells it `TEXT`.

## 2. What to build

Add to `src/sqldialect.rs`:

```rust
/// Why a canonical type cannot be written for a dialect.
#[derive(Debug, Clone, PartialEq, Eq)]
pub struct UnsupportedType {
    pub dialect: Dialect,
    /// The canonical base that could not be rendered.
    pub base: String,
    /// Why not, phrased for someone reading an error.
    pub reason: String,
}

impl std::fmt::Display for UnsupportedType { /* see §5 */ }

impl Dialect {
    /// Write a canonical type as this engine's own type text.
    pub fn render_type(&self, ty: &CanonicalType) -> Result<String, UnsupportedType>;
}
```

`CanonicalType` comes from `crate::sqltype`.

### 2.1 The rule that governs every decision here

**Render the engine's own name for the same type. Refuse when the engine does
not have the type. Never substitute something close.**

A refusal is a normal, useful answer — the caller reports "MySQL has no
`interval` type" and a person fixes it. A silent substitution produces a column
that looks right and holds different data, which is the failure this project
exists to avoid. In particular:

- **Never widen to make something fit.** `tinyint` must not become `smallint`
  on PostgreSQL. It is a different type with a different range.
- **Never change the character encoding.** `nvarchar` must not become `varchar`.

The one thing that *is* allowed is a different **name** for a type the engine
genuinely has, where nothing is lost. SQL Server's `bit` really is a boolean;
MySQL's `decimal` really is `numeric`.

### 2.2 An unrecognised canonical type is always a refusal

If `ty.recognised` is `false`, return `Err` immediately, whatever the dialect.
The base is a string nobody has vetted — `geography`, `hstore`, a user-defined
type — and guessing at it is exactly what §2.1 forbids. Reason text:

```
`geography` is not a type this tool recognises, so it cannot be written for PostgreSQL
```

## 3. The rendering table

`{n}` is the first parameter, `{p}` and `{s}` the first and second. `MAX` means
the parameter equals `sqltype::UNBOUNDED`.

### Integers — never carry parameters

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `integer` | `integer` | `int` | `int` | `integer` |
| `bigint` | `bigint` | `bigint` | `bigint` | `bigint` |
| `smallint` | `smallint` | `smallint` | `smallint` | `smallint` |
| `tinyint` | refuse | `tinyint` | `tinyint` | `tinyint` |
| `mediumint` | refuse | `mediumint` | refuse | `mediumint` |

SQLite accepts any type name and applies affinity rules, so it renders whatever
the canonical name is. That is not laziness: SQLite stores the declared text
verbatim, so writing `tinyint` there is exactly what a SQLite user would write.

### Exact numerics

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `numeric` | `numeric` | `decimal` | `decimal` | `numeric` |

Parameters pass through when present: two parameters render `(p, s)`, one
renders `(p)`, none renders the bare name. A `numeric` with no parameters is
valid on PostgreSQL and SQLite; on MySQL and SQL Server a bare `DECIMAL`
defaults to `(10,0)`, which is a real difference — but it is the engine's own
default for the same type, not a substitution this code made, so render it and
say nothing.

### Approximate numerics

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `real` | `real` | `float` | `real` | `real` |
| `double precision` | `double precision` | `double` | `float` | `double precision` |

The SQL Server column is not a mistake and is the one place to be careful:
SQL Server's `real` is 4-byte and its `float` is 8-byte by default. So
`double precision` renders as SQL Server `float`. Put that in a comment; it
looks like a bug to anyone who has not just read it.

### Character types

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `varchar` with `{n}` | `varchar({n})` | `varchar({n})` | `varchar({n})` | `varchar({n})` |
| `varchar` with `MAX` | `text` | `longtext` | `varchar(max)` | `text` |
| `varchar` with no parameter | `text` | refuse | refuse | `text` |
| `char` with `{n}` | `char({n})` | `char({n})` | `char({n})` | `char({n})` |
| `text` | `text` | `text` | `varchar(max)` | `text` |
| `nvarchar` with `{n}` | refuse | refuse | `nvarchar({n})` | `nvarchar({n})` |
| `nvarchar` with `MAX` | refuse | refuse | `nvarchar(max)` | `nvarchar(max)` |
| `nchar` with `{n}` | refuse | refuse | `nchar({n})` | `nchar({n})` |

Three of those rows need their reasoning recorded in comments:

- **`varchar` with no parameter.** PostgreSQL treats bare `varchar` as unlimited,
  so `text` is the honest rendering. MySQL and SQL Server require a length and
  have no unlimited `varchar`, so there is nothing correct to write — refuse.
- **`text` on SQL Server.** SQL Server has a `text` type but it is deprecated and
  Microsoft documents it as slated for removal. `varchar(max)` is the supported
  equivalent.
- **The `n`-prefixed types.** These are UTF-16 on SQL Server. PostgreSQL and
  MySQL handle encoding through the database or column charset rather than the
  type, so there is no type to map to. Rendering plain `varchar` would silently
  change the encoding, which §2.1 forbids.

### Boolean

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `boolean` | `boolean` | `boolean` | `bit` | `boolean` |

MySQL accepts `BOOLEAN` as written and stores it as `tinyint(1)`; render
`boolean` because that is what a person writes. SQL Server has no boolean type
and `bit` is its exact equivalent — one bit, two states — so this is a rename,
not a substitution.

### Everything else

Any canonical base not in the tables above returns `Err` with the reason:

```
`interval` is not supported by this version for MySQL
```

0.7c replaces those refusals with real renderings for the temporal, binary and
structured types. Do not add them here.

## 4. Refusal messages

`UnsupportedType::reason` is a sentence someone can act on. Use these shapes:

| Case | Reason text |
| --- | --- |
| Unrecognised base | ``base` is not a type this tool recognises, so it cannot be written for {dialect}` |
| Engine lacks the type | `{dialect} has no `{base}` type` |
| Needs a length it does not have | ``{base}` needs a length on {dialect}, and none was declared` |
| Not yet implemented | ``{base}` is not supported by this version for {dialect}` |

`{dialect}` is `Dialect::name()`, so `PostgreSQL` and `SQL Server` with their
real spellings.

## 5. `Display`

```
MySQL has no `mediumint` type
```

Just the reason. The struct keeps `dialect` and `base` as fields so a caller can
group or filter refusals without parsing text.

---

## 6. Non-goals

- **No dates, times, binary or structured types.** Those are 0.7c.
- **No DDL.** This renders a type, not a column definition, and certainly not a
  statement. Nothing here writes `NOT NULL` or `DEFAULT`.
- **No changes outside `src/sqldialect.rs`.**
- **No new dependencies.**

## 7. Tests

In `src/sqldialect.rs`. Prefix them so they group together.

| Test name | Must assert |
| --- | --- |
| `each_engine_writes_its_own_name_for_the_same_type` | `numeric(12,2)` renders `numeric(12, 2)` on PostgreSQL and `decimal(12, 2)` on MySQL; `integer` renders `integer` on PostgreSQL and `int` on MySQL |
| `a_length_is_carried_through` | `varchar(50)` renders `varchar(50)` on all four |
| `an_unbounded_string_uses_each_engines_own_spelling` | `varchar(max)` renders `text` on PostgreSQL, `longtext` on MySQL, `varchar(max)` on SQL Server |
| `sql_server_float_is_eight_bytes_and_real_is_four` | `double precision` renders `float` on SQL Server, and `real` renders `real`. Comment: this looks inverted unless you know SQL Server's widths |
| `deprecated_types_are_not_emitted` | `text` renders `varchar(max)` on SQL Server, never `text` |
| `a_type_the_engine_lacks_is_refused_rather_than_widened` | `tinyint` on PostgreSQL is `Err`; the reason names both. Assert it is **not** `smallint`. Comment: widening changes the range, and a column that quietly holds more than it should is the failure this refuses to make |
| `a_national_character_type_is_not_downgraded_to_ascii` | `nvarchar(50)` on PostgreSQL and MySQL is `Err`, and the error text does not contain `varchar` |
| `an_unrecognised_type_is_never_guessed_at` | `sqltype::canonical("geography")` renders `Err` on all four dialects |
| `a_string_with_no_length_is_refused_where_a_length_is_required` | bare `varchar` renders `text` on PostgreSQL and SQLite, `Err` on MySQL and SQL Server |
| `boolean_is_a_bit_on_sql_server` | `boolean` renders `bit` on SQL Server and `boolean` on the other three |
| `a_refusal_says_which_engine_and_which_type` | An `Err` from any case has `dialect` and `base` set, and `to_string()` contains the engine's display name |
