# Spec: freeze the public API

**Target release:** 0.9
**Repository:** `bijection` (free crate)
**Depends on:** 0.9a, 0.9b and 0.9c, which are the last specs that change the
shape of the public types. 0.9d and 0.9e are documentation and can be in any
order relative to this, but doing them first makes the inventory in part two
much easier to write.
**Size:** a list of attributes to apply, a few constructors, and one new
document. Mechanical, with the judgement already made — every decision is
written out below rather than left to you.

---

## 1. Why

1.0 means the Rust API is stable. After it, adding a field to a struct or a
variant to an enum is a breaking change requiring 2.0 — unless the type says in
advance that it may grow.

This crate's types will grow. `TableCatalog` went from columns alone to
constraints, indexes and unread kinds in one release. `CatalogAvailability`
gained `TableNotFound`. `Constraint` is gaining `ForeignKey` in 0.9a. The next
release will find something else, and pretending otherwise now costs a major
version later.

Two types already say so — `TableCatalog` and `SchemaDiffResult`. This makes the
rest agree with them.

---

## 2. Part one: apply `#[non_exhaustive]`

Add the attribute to each item below. This is the complete list; do not add it
to anything not named here, and do not leave out anything that is.

### `src/catalog.rs`

| Item | Why it will grow |
| --- | --- |
| `Constraint` | Exclusion constraints, deferrability, `NOT VALID` |
| `ConstraintKind` | One per `Constraint` variant, by construction |
| `ReferentialAction` | It has an `Other` variant, but a real action promoted out of `Other` into its own variant is still a new variant |
| `MetadataChange` | Four variants were added in 0.6 alone |
| `CatalogAvailability` | Already grew once |
| `TypeImpact` | A third classification between widening and narrowing is plausible |
| `ColumnDef` | Collation, comment, generated-column expression — all named in 0.9c as things not yet read |
| `IndexDef` | Partial-index predicates, index method, sort order |

### `src/sqltype.rs`

| Item | Why |
| --- | --- |
| `CanonicalType` | Built by `canonical()`, which is the constructor a caller should be using anyway |

### `src/sqldialect.rs`

| Item | Why |
| --- | --- |
| `Dialect` | A fifth engine is a feature, not a major version |
| `UnsupportedType` | An error's fields are the first thing to grow |

### `src/schema.rs` and `src/data.rs`

| Item | Why |
| --- | --- |
| `SchemaDiffError` | Every error enum grows |
| `ConnectorError` (wherever it is defined) | Same |
| `ExportFormat`, `FailOn`, `ManifestFormat` | Cheap now, and each is a plausible place for a third option |

### The constructors this needs

`#[non_exhaustive]` on a struct stops code outside the crate building it with a
struct literal. `TableCatalog` already answers that with `new` plus `with_`
methods. `ColumnDef` and `IndexDef` need the same, or nothing outside the crate
can build one — including the paid crate's tests, which do.

```rust
impl ColumnDef {
    pub fn new(
        name: String,
        data_type: String,
        nullable: bool,
        default: Option<String>,
        ordinal: u32,
    ) -> Self
}

impl IndexDef {
    pub fn new(name: String, columns: Vec<String>, unique: bool) -> Self
}
```

All fields positional, none defaulted. A builder whose unset `nullable` quietly
means `true` would be a plausible default standing in for a value nobody
supplied, which is the thing this codebase does not do. Five arguments is not
elegant and is the right trade here; say so in a comment so nobody
"improves" it.

Do **not** convert existing struct literals inside this crate to use them. The
attribute does not apply within the defining crate, the literals are fine, and
churning several hundred lines of test fixtures would bury the change.

### What is deliberately not on the list

`SourceConfig` in `src/connectors/mod.rs`. It is `#[non_exhaustive]`-shaped —
new engines will arrive — but the desktop app is a separate crate that
constructs and matches it, and working out that blast radius is not this spec's
job. **Leave it alone and note it in your report** so it gets a decision of its
own.

## 3. Part two: an inventory of the public surface

Write `docs/api-surface.md`. A survey, not a set of changes.

One table, one row per public item, sorted by module then name:

| Column | Contents |
| --- | --- |
| Item | `catalog::TableCatalog::with_unread` |
| Kind | struct / enum / variant / method / function / const / type alias |
| Used outside its own module? | yes / no |
| Used outside the crate? | yes / unknown |

For the third column, search the whole repository including `tests/` and
`tauri-app/`. For the fourth, `yes` where you can point at a use in `tests/` or
`tauri-app/`, `unknown` otherwise — you cannot see the paid crate or anyone
else's code, and **`unknown` is the honest entry, not `no`**. Do not guess.

Above the table, a short paragraph saying what the file is for: a snapshot taken
before 1.0, to decide what should stay public. Say when it was generated and
against which version, because it goes stale the moment anything changes and a
reader needs to know whether to trust it.

**Change nothing based on it.** Do not remove an item, narrow a visibility, or
add `#[doc(hidden)]`. Several items are public precisely so a downstream binary
can use them — `cli::Commands` and `cli::dispatch` exist for exactly that, and
its module header says so. The rows that look removable are a decision for the
project lead, and this file is what that decision gets made from.

---

## 4. Non-goals

- **No renames.** Not one, however wrong a name looks. Say it in your report.
- **No visibility changes, no removals, no deprecations.**
- **No behaviour changes.** After this, every existing test passes untouched. If
  one does not, the change went further than the spec.
- **Do not touch `src/connectors/` except to read it** for the inventory.
- **Do not touch `tauri-app/` at all**, including its lockfile.
- **No new dependencies.**

---

## 5. Tests

Little to test — attributes have no runtime behaviour. Two things are worth
asserting anyway:

| Test name | Must assert |
| --- | --- |
| `a_column_definition_can_be_built_through_its_constructor` | `ColumnDef::new` produces a value equal to the equivalent struct literal |
| `an_index_definition_can_be_built_through_its_constructor` | The same for `IndexDef::new` |

They look trivial. They are the compile-time proof that the constructors take
every field, so a field added later cannot be forgotten in the constructor and
left at a default nobody chose.
