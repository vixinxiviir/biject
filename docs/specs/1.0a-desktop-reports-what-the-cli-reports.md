# Spec: the desktop app reports what the CLI reports

**Target release:** 1.0
**Repository:** `bijection` (free crate) — **`tauri-app/` only**
**Depends on:** nothing. 0.9.0 shipped the data this reads.
**Size:** one renderer, one label table, one new section. Small, and it is
JavaScript rather than Rust — the first spec in this project that is.

---

## 1. The gap

This is a live defect, not a missing feature. 0.9.0 added two things to
`biject schema` and the desktop app shows neither, while showing everything
around them — so it reports *less* than the CLI and does not say so.

**A foreign key renders as the bare word `foreign_key`.** In
`tauri-app/ui/index.html`, `describeConstraint` handles `primary_key`, `unique`
and `check`, then falls through to `default: return c.kind`. The Schema Metadata
table therefore shows a row reading

```
foreign_key    foreign_key missing from target    breaking
```

with no columns, no referenced table, no referential actions. The user is told
something breaking happened and cannot see what.

**The scope footer is absent entirely.** `grep -c "scope" tauri-app/ui/index.html`
returns 0. Every CLI run now ends with what a schema comparison never examines;
the app ends with nothing, so a clean result there still reads as "these schemas
match".

Both were out of scope for the specs that introduced them, correctly — those
specs were about the library. The result is still that the app under-reports,
and this is the project's own bar: **the tool must not give a partial answer
without saying so.** A second interface is still the tool.

## 2. What to build

Everything is in `tauri-app/ui/index.html`. **No Rust changes.** The data is
already in the JSON the app receives; nothing needs to be sent that is not
already sent.

### 2.1 Render a foreign key

`describeConstraint(c)` gains a `foreign_key` case. The shape it receives, from
serde's internally-tagged representation of `Constraint`:

```json
{
  "kind": "foreign_key",
  "name": "orders_customer_id_fkey",
  "columns": ["customer_id"],
  "referenced_table": "public.customers",
  "referenced_columns": ["id"],
  "on_delete": "cascade",
  "on_update": "no_action"
}
```

Render it as the CLI does:

```
FOREIGN KEY (customer_id) REFERENCES public.customers(id) ON DELETE CASCADE
```

An `ON DELETE` or `ON UPDATE` that is `no_action` is **left off**, matching how
a database prints its own definition and how `Constraint`'s `Display` renders it
in the CLI. Both clauses off is the common case.

### 2.2 The referential action is not always a string

**This is the part to get right.** `ReferentialAction` is an ordinary Rust enum
with a `snake_case` rename, so its unit variants serialise as plain strings —
`"no_action"`, `"restrict"`, `"cascade"`, `"set_null"`, `"set_default"` — but
its `Other` variant is a newtype and serialises as an **object**:

```json
"on_delete": { "other": "SOMETHING_ELSE" }
```

That variant exists because an action the connectors do not recognise is kept
verbatim rather than folded into `NO ACTION`, which would be a claim about what
a real delete does to real rows. Rendering `[object Object]` there would undo
the whole point.

Write one small function that turns either shape into display text: a string
becomes its upper-case form with underscores as spaces (`set_null` →
`SET NULL`), and an object yields the value of its single key, verbatim and
unchanged. Anything else — null, undefined, an unexpected shape — must produce
something visibly wrong rather than empty; return the JSON of it.

### 2.3 The kind label

`describeConstraintKind` maps a `ConstraintKind` to a plural label and is used
by the "Not Compared, Because the Source Cannot Report Them" section. It is
missing `foreign_key`, so a connector that cannot read foreign keys currently
lists the raw string. Add `'foreign_key' → 'foreign keys'`.

The comment above that function says it matches `ConstraintKind`'s `Display` on
the Rust side. Keep that true.

### 2.4 The scope footer

`SchemaDiffResult` now carries:

```json
"scope": {
  "compared": ["column names", "declared types", "...", "foreign keys"],
  "not_compared": ["triggers", "views and materialised views", "..."]
}
```

Add a section after the existing metadata sections, in the same style as
`s-section-metadata-unread`. It renders `scope.not_compared` as a list, and
**it is always visible** — unlike its neighbours, which hide when empty. A clean
comparison is the run that most needs it.

Give it a heading that distinguishes it from the two sections above it, which
are about *this run*: "Schema Metadata Not Compared" is a catalog that could not
be read, "Not Compared, Because the Source Cannot Report Them" is a kind this
engine will not expose, and this new one is what the tool never examines on any
run, on any engine. Wording along the lines of **"Never Compared, On Any Run"**,
with one line of explanation, keeps the three apart.

If `scope` is absent — an older result, or a caller that built one by hand —
show nothing rather than an empty list. That is the one case where silence is
right, because the alternative is asserting a scope you were not given.

## 3. Non-goals

- **No Rust changes at all.** If you find yourself needing one, the data is
  already there and you have missed it; say so rather than reaching for
  `src/`.
- **Do not add `batch`, `--policy` or export to the app.** That is 1.0b, and it
  is a decision that has been taken separately.
- **Do not restyle anything.** Match the existing sections.
- **No new dependencies**, and no build step. This file is plain HTML, CSS and
  JavaScript served as-is.
- **Do not touch `tauri-app/src-tauri/`** — the commands already return what is
  needed.

## 4. Tests

This file has no test harness and this spec does not add one. Verify by running
the app, and report what you saw.

Build one SQLite database with three tables:

```sql
CREATE TABLE parent (id INTEGER PRIMARY KEY);
CREATE TABLE orders_a (
  id INTEGER PRIMARY KEY,
  parent_id INTEGER,
  FOREIGN KEY (parent_id) REFERENCES parent(id) ON DELETE CASCADE
);
CREATE TABLE orders_b (id INTEGER PRIMARY KEY, parent_id INTEGER);
```

Then, with the app pointed at `orders_a` and `orders_b` as source and target:

| What to check | Expected |
| --- | --- |
| The metadata row for the key | `FOREIGN KEY (parent_id) REFERENCES parent(id) ON DELETE CASCADE missing from target`, marked breaking |
| The same comparison in the CLI | the same text — run `biject schema --source sqlite://…` and compare word for word |
| The unread section | names "check constraints", since SQLite cannot report them, and does **not** name foreign keys |
| The new scope section | present, listing triggers, views, collations and the rest |
| Two identical tables | the scope section is still there |
| Two CSV files | the scope section is still there, alongside the "no catalog" gap |

For the `Other` action shape, you will not get one from a real engine — that is
what it is for. Check it by hand: temporarily feed the renderer
`{ "other": "SOMETHING_ELSE" }` in the browser console, confirm it prints
`SOMETHING_ELSE`, and put the code back.

## 5. Acceptance

The app has to actually run:

```bash
cargo run --manifest-path tauri-app/src-tauri/Cargo.toml
```

```bash
cargo check --manifest-path tauri-app/src-tauri/Cargo.toml
```

The free crate is untouched, so its suite should be unaffected — run it anyway
to prove that:

```bash
cargo test --all-targets
```

```bash
git diff --stat
```

Expected files: `tauri-app/ui/index.html`. Nothing else. If `src/` or
`tauri-app/src-tauri/` appears, stop and explain why.

## 6. What to hand back

1. A screenshot or a transcription of the Schema Metadata row for the foreign
   key, and of the new scope section.
2. The CLI's output for the same two tables, so the two can be read side by
   side. **They should say the same thing.** If they do not, say so — that is
   the finding, not a detail.
3. Anything the app shows that the CLI does not, or the reverse, that this spec
   did not mention.
