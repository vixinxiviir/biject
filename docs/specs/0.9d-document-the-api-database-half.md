# Spec: document the public API — the database-knowledge half

**Target release:** 0.9
**Repository:** `bijection` (free crate)
**Depends on:** 0.9a and 0.9b. Documenting `Constraint` before it has its final
set of variants means writing the same comment twice.
**Size:** roughly fifty doc comments across five files, plus a handful of
doctests. No behaviour changes at all.

---

## 1. The gap

`biject` is a published library as well as a binary. Its docs.rs page is what
somebody sees before deciding whether to depend on it, and today it is a list of
type names with nothing beside them. Under `-W missing_docs` the crate produces
around two hundred warnings.

1.0 means the Rust API is stable. An API nobody can read is not one anybody
should be asked to depend on.

This spec covers the half of the crate that is knowledge about databases:
`catalog`, `sqltype`, `sqldialect`, and the connector surface. 0.9e covers the
comparison and command half and turns the lint on.

---

## 2. Scope

Document every public item in:

- `src/catalog.rs`
- `src/sqltype.rs`
- `src/sqldialect.rs`
- `src/connectors/mod.rs`
- `src/connectors/profiles.rs`
- `src/connectors/postgres.rs` (one item)

Including: module headers where absent, public structs, enums, their variants,
their public fields, and public functions and methods.

To see the list:

```bash
RUSTFLAGS="-W missing_docs" cargo check --lib 2>&1 | grep -A 1 "missing documentation"
```

Several of these files already have good comments on their harder parts. **Do
not rewrite an existing doc comment.** Add what is missing. If you think an
existing one is wrong, say so in your report and leave it.

---

## 3. What a doc comment here has to do

The house style is already in the codebase — read the comment on
`Constraint::identity` or on `CatalogAvailability` before writing anything.

- **Say what the thing is, not what its name already says.** `/// The column
  name.` on a field called `name` is worse than nothing: it adds a line to every
  reader's scroll and tells them what they knew. If that is genuinely all there
  is to say, say the thing the name does not: the units, the base, the ordering,
  what it is when absent. `ordinal` already does this well — "1-based position,
  so column reordering is visible."
- **Prefer the constraint over the description.** The most useful sentence is
  usually the one that stops a misuse: names are engine-generated so do not
  compare them; the expression is the catalog's spelling and not what was typed;
  this is a `BTreeMap` so iteration order is by column name.
- **On an enum, document the variants, not just the enum.** The reason a variant
  exists separately from its neighbour is the whole content.
- **Keep it short.** One or two sentences for most items. The long ones in this
  crate are long because they record a decision, not because length is a virtue.

### The rule that matters more than the style

**If you cannot say what an item does from reading the code, do not write a doc
comment for it.** Leave it undocumented, and list it in your report as something
that needs the author.

An invented description is worse than a missing one: it will be believed, it
will be copied into someone's code, and nothing will contradict it. This is the
same failure the whole project is organised against — a confident answer that
was never checked — and a doc comment is the one place where producing it costs
nothing and catches nobody.

## 4. Doctests

These three modules contain pure functions, which means their documentation can
be executable rather than merely plausible.

Add a doctest to each of:

- `sqltype::canonical` — one showing two spellings of the same type folding
  together, and one showing an unrecognised type coming back with `recognised`
  false rather than being guessed at.
- `sqldialect::Dialect::quote_ident` — one showing an identifier containing the
  engine's own escape character.
- `sqldialect::Dialect::render_type` — one successful render, and one showing a
  type the dialect does not have coming back as an error rather than a
  substitute.
- `catalog::TableCatalog` — the builder chain, since the type is
  `#[non_exhaustive]` and a struct literal will not compile. Somebody will try;
  the doc comment is where they find out why not.
- `catalog::CatalogAvailability::explain` — showing that the `Available` case
  returns `None`.

They must pass under `cargo test --doc`. Keep each to a few lines. A doctest
needing a database connection is not a doctest — for anything in
`connectors/mod.rs`, write prose.

`sqltype::UNBOUNDED` deserves particular care. Its whole reason to exist is that
a length sentinel written into SQL produces a number no engine will accept, and
a caller who does not know it exists is the person who will do that.

---

## 5. Non-goals

- **No behaviour changes.** Not a rename, not a signature, not a visibility
  change, not a `#[non_exhaustive]`. Sealing the API is 0.9f, deliberately
  separate so this diff can be read as pure documentation.
- **Do not turn the lint on.** `#![deny(missing_docs)]` lands in 0.9e, when the
  whole crate can satisfy it. Turning it on here breaks the build for the files
  0.9e has not reached.
- **Do not reorder items** to group documented ones together.
- **Do not add `#[doc(hidden)]`** to make a warning go away. If an item should
  not be public, say so in your report; that is 0.9f's decision.
- **No new dependencies.**


```bash

```

Then show the count coming down. Before your change it is around two hundred:

```bash
RUSTFLAGS="-W missing_docs" cargo check --lib 2>&1 | grep -c "missing documentation"
```

Run it before and after and report both numbers. Then confirm none of the
remaining warnings point at the five files above:

```bash
RUSTFLAGS="-W missing_docs" cargo check --lib 2>&1 | grep "^  --> " | sed 's/:.*//' | sort | uniq -c
```

The five files in section 2 must not appear.

```bash
cargo doc --no-deps --open
```

Read the generated page for `catalog` before you call this done. Documentation
is checked against what it renders, not against what it looked like in the
source — this project has already found three cases of documentation that
described intent rather than behaviour.

```bash
git diff --stat
```

Expected files: the five in section 2. Nothing else. Every line in that diff
should begin with `///`, `//!`, or be blank.

## 7. What to hand back

The usual report, plus one thing specific to this spec: **the list of items you
left undocumented because you could not tell what they do.** That list is the
most valuable output here. An empty list is a fine answer if it is true, and a
suspicious one if it is not.
