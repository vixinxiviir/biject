# Spec: compare a schema without downloading the table

**Target release:** 0.8
**Repository:** `bijection` (free crate)
**Depends on:** nothing. Can be done at any time, in any order.
**Size:** one new function in `src/connectors/mod.rs`, one small change in each
of the four connectors, one call site changed in `src/schema.rs`

**This spec authorises changes to `src/connectors/`**, which the standing brief
otherwise forbids.

---

## 1. The problem

`biject schema` compares two schemas. To do it, it calls `load_source`, which
runs `SELECT * FROM <table>` and pulls **every row across the network** into
memory — then uses nothing but the column names and types.

On a CSV that is harmless. On a production table it is a catastrophe: a
hundred-million-row table means gigabytes transferred and held in memory, and a
query that may run for minutes, to answer a question that needs zero rows.

You can see the shape of it in `src/connectors/postgres.rs::normalize_query`: a
bare table reference becomes `SELECT * FROM t`, with no limit anywhere.

This became fixable in 0.6. Before then, a zero-row result produced a DataFrame
with no columns, so the schema had to be inferred from actual rows. Now every
connector takes its column list from the statement's description and returns a
correctly shaped, empty frame. A zero-row query gives exactly the same schema as
a full one.

## 2. What to build

### 2.1 A schema-only load path

In `src/connectors/mod.rs`:

```rust
/// Load a source's shape without transferring its contents.
///
/// Returns a DataFrame with the right columns and types and no rows. For a
/// schema comparison that is everything needed, and it turns a full table scan
/// into a metadata lookup.
pub async fn load_schema_only(config: &SourceConfig) -> Result<DataFrame, ConnectorError>
```

It dispatches exactly as `load_source` does, but calls a new `load_schema_async`
on each database connector. `SourceConfig::File` delegates straight to the
existing CSV loader — a local file has no transfer cost and Polars needs rows to
infer CSV types, so nothing changes there.

### 2.2 Per-connector: a zero-row form of the query

Each database connector gains a function that builds the zero-row query, then
runs it through the code path it already has. The only new logic is the SQL.

`normalize_query` in each connector already distinguishes a bare table reference
from a `SELECT`/`WITH` statement. Keep that distinction — it decides which of two
forms to use:

**A bare table reference** — the common case, and the safe one:

| Engine | Zero-row query |
| --- | --- |
| PostgreSQL | `SELECT * FROM <table> LIMIT 0` |
| MySQL | `SELECT * FROM <table> LIMIT 0` |
| SQLite | `SELECT * FROM <table> LIMIT 0` |
| SQL Server | `SELECT TOP 0 * FROM <table>` |

**A `SELECT` or `WITH` statement** — wrap it as a subquery:

| Engine | Zero-row query |
| --- | --- |
| PostgreSQL | `SELECT * FROM (<query>) AS biject_schema_probe LIMIT 0` |
| MySQL | `SELECT * FROM (<query>) AS biject_schema_probe LIMIT 0` |
| SQLite | `SELECT * FROM (<query>) AS biject_schema_probe LIMIT 0` |
| SQL Server | `SELECT TOP 0 * FROM (<query>) AS biject_schema_probe` |

The alias is required: PostgreSQL and SQL Server both reject an unaliased
subquery. Use that exact name so it is recognisable in a server log.

### 2.3 The one case that can fail, and what to do about it

A user-supplied `SELECT` ending in `ORDER BY` is legal on its own and **illegal
inside a subquery on SQL Server**. Wrapping it produces:

```
The ORDER BY clause is invalid in views, inline functions, derived tables,
subqueries, and common table expressions, unless TOP ... is also specified.
```

Do not try to detect or rewrite the `ORDER BY` — parsing SQL to find out whether
a trailing `ORDER BY` belongs to the outer query is not something to attempt
here. Let the query fail, and make the failure explain itself: when the
schema-only query fails **and** the original query was a statement rather than a
bare table reference, return the error with this added context:

```
This was a schema comparison, which wraps the query to avoid transferring rows.
A query ending in ORDER BY cannot be wrapped on SQL Server. Remove the ORDER BY
— a schema comparison does not depend on row order.
```

Attach it for every engine, not just SQL Server: the advice is correct anywhere
the wrapped form fails, and hard-coding one engine's error text is worse than a
sentence that is occasionally redundant.

### 2.4 The call site

In `src/schema.rs::schema_diff`, the two `load_source` calls become
`load_schema_only`. Nothing else in that function changes.

**Leave `src/data.rs` alone.** The `data` command compares rows and needs them.

---

## 3. Non-goals

- **Do not change `load_source`.** It stays exactly as it is; this adds a second
  path beside it.
- **Do not touch the `data` or `batch` commands.**
- **Do not remove the catalog read.** `schema_diff` reads catalogs separately for
  constraints and declared types. That stays.
- **No new dependencies.**
- Do not try to skip executing the query entirely. PostgreSQL and SQLite could in
  principle describe a prepared statement without running it, and that would be
  even cheaper — but it is a different shape of change per driver and is not this
  spec.

## 4. Tests

### 4.1 Unit tests, no server needed

Put these beside the existing `normalize_query` tests in each connector.

| Test name | Must assert |
| --- | --- |
| `a_bare_table_becomes_a_zero_row_select` | PostgreSQL/MySQL/SQLite produce `SELECT * FROM orders LIMIT 0`; SQL Server produces `SELECT TOP 0 * FROM orders` |
| `a_statement_is_wrapped_rather_than_appended_to` | Input `SELECT a FROM t WHERE b > 1` produces the aliased subquery form for that engine, and the original text appears inside it unmodified |
| `the_subquery_alias_is_present` | Every wrapped form contains `biject_schema_probe`. Comment: PostgreSQL and SQL Server reject an unaliased derived table |

### 4.2 SQLite integration, no container needed

In `src/connectors/sqlite.rs`, using a real file the way the existing SQLite
tests do:

| Test name | Must assert |
| --- | --- |
| `a_schema_only_load_returns_the_columns_and_no_rows` | Create a table, insert three rows, `load_schema_only` returns `height() == 0` and the full column list in order |
| `a_schema_only_load_agrees_with_a_full_load` | For the same table, the column names and dtypes from `load_schema_only` are identical to those from `load_source`. Comment: if these ever diverge, a schema comparison starts depending on how many rows happen to be in the table |
| `a_schema_only_load_of_a_query_keeps_the_querys_columns` | `SELECT id AS renamed FROM t` yields exactly one column named `renamed` |

### 4.3 PostgreSQL integration

Add to `tests/catalog_postgres.rs`, `#[ignore]` like its neighbours.

| Test name | Must assert |
| --- | --- |
| `a_schema_only_load_matches_a_full_load_on_a_real_server` | Against the existing `dev` fixture: same column names, same dtypes, zero rows |

You are not expected to run this one — say in your report that you did not, and
the reviewer will. The SQLite tests above cover the same logic without a server.

### 4.4 Existing tests

Every one must still pass untouched, in particular the 0.6 tests asserting that
an empty table still reports its columns. Those are what make this change safe;
if one breaks, this change is unsafe.

### A demonstration to include in your report

Build a SQLite database with a table of at least 50,000 rows, then run:

```bash
cargo run -- schema --source sqlite://big.sqlite --source-query a --target sqlite://big.sqlite --target-query b
```

Report the wall-clock time before and after your change. It should drop
sharply, and the output must be identical. If the output differs in any way,
stop — that is the failure this whole change has to avoid.
