# Spec: foreign keys — the model, and reading them on PostgreSQL

**Target release:** 0.9
**Repository:** `bijection` (free crate)
**Depends on:** nothing.
**Size:** one enum variant, one supporting enum, one catalog query, tests. The
model work is small; getting the referential actions right is the fiddly part.

---

## 1. The gap

`biject schema` reads primary keys, unique constraints, check constraints and
indexes. It does not read foreign keys, and it does not say that it does not.

Point it at two PostgreSQL tables where the target has lost its
`orders_customer_id_fkey` and it prints a comparison with no mention of it. The
report reads as "these two tables agree about their rules". They do not: one
guarantees every `customer_id` matches a real customer and the other does not.

That is the exact failure this project is built to avoid, and it is the largest
one left in the free crate.

The code comments in `src/catalog.rs` and the connectors say foreign keys are
"deliberately absent". That decision was made when the only consumer was
migration generation, where a foreign key means ordering DDL across tables —
genuinely a different program. **Reporting one is not generating DDL for one.**
This spec makes the tool read and report them. It does not make anything
generate a foreign key.

## 2. What to build

### 2.1 `ReferentialAction`

New public enum in `src/catalog.rs`, next to `ConstraintKind`.

```rust
/// What the database does to the referencing rows when the referenced row is
/// deleted or its key updated.
#[derive(Debug, Clone, PartialEq, Eq, Serialize)]
#[serde(rename_all = "snake_case")]
pub enum ReferentialAction {
    NoAction,
    Restrict,
    Cascade,
    SetNull,
    SetDefault,
    /// Something the engine reported that this does not recognise.
    ///
    /// Carries the engine's own text. A value folded into `NoAction` because
    /// it was not in the list would be a silent claim about what happens to
    /// real rows on a real delete.
    Other(String),
}
```

`Display` renders the SQL spelling: `NO ACTION`, `RESTRICT`, `CASCADE`,
`SET NULL`, `SET DEFAULT`, and for `Other`, the text as given.

**Read that `Other` variant as an instruction about the whole task.** Every
mapping in this spec is from an engine's own vocabulary into this one, and every
one of them can meet a value the table below does not list. Nothing gets a
plausible default.

### 2.2 The constraint variant

Add to `Constraint` in `src/catalog.rs`:

```rust
/// A reference from this table's columns to another table's.
ForeignKey {
    name: String,
    /// Columns in *this* table, in key order.
    columns: Vec<String>,
    /// The table referenced, as the engine reports it. Schema-qualified when
    /// the engine gives a schema.
    referenced_table: String,
    /// Columns in the referenced table, paired positionally with `columns`.
    referenced_columns: Vec<String>,
    on_delete: ReferentialAction,
    on_update: ReferentialAction,
},
```

Add `ConstraintKind::ForeignKey` and extend `ConstraintKind::ALL` to five.
Its `Display` label is `foreign keys`.

Update the existing `impl Constraint` methods:

- `kind()` — returns `ConstraintKind::ForeignKey`.
- `name()` — returns the name.
- `columns()` — returns the **local** columns. The doc comment currently says
  "empty for a `CHECK`"; extend it to say a foreign key reports the columns on
  this side, because that is the side this table is being compared on.
- `identity()` — the tuple is
  `("foreign_key", "<columns> -> <referenced_table>(<referenced_columns>) ON DELETE <a> ON UPDATE <a>")`.
  Names stay excluded for the reason already documented there: engines invent
  them. The actions are part of the identity because two keys onto the same
  column that differ in `ON DELETE` do genuinely different things to data.
- `Display` — `FOREIGN KEY (customer_id) REFERENCES customers(id) ON DELETE CASCADE`.
  Omit an `ON DELETE` or `ON UPDATE` clause that is `NoAction`, matching how a
  database prints its own definition.

### 2.3 The cross-engine caveat

Write it into the `ForeignKey` variant's doc comment, in the same spirit as the
one already on `Check`:

`referenced_table` is the engine's own spelling. PostgreSQL reports
`public.customers`, SQL Server `dbo.customers`, SQLite a bare `customers`. Two
identical keys therefore compare unequal across engines. That is a known limit
of comparing two different engines and is not something to normalise away here —
guessing that `public` and `dbo` mean the same thing is a claim about someone's
schema layout, not a fact.

### 2.4 Breaking or not

`MetadataChange::ConstraintMissing` and `ConstraintExtra` already carry a
`Constraint`, and `is_breaking` already classifies by variant of the *change*,
not of the constraint. **Do not add a special case.** A foreign key the source
enforces and the target does not is breaking for exactly the reason the existing
comment gives: the target can hold rows the source could not.

### 2.5 Every connector that cannot read one must say so

This is the part that must not be skipped. The instant `ConstraintKind` gains
`ForeignKey`, every connector that does not read foreign keys is reporting an
empty list of them — which reads as "this table has none".

`src/connectors/postgres.rs` gains reading, below. **`mysql.rs`, `sqlserver.rs`
and `sqlite.rs` must each push `ConstraintKind::ForeignKey` onto their `unread`
list in this same change**, so that until 0.9b lands they say "not looked at"
rather than "none". Their existing `with_unread` calls show where; `sqlite.rs`
already passes `vec![ConstraintKind::Check]` and becomes
`vec![ConstraintKind::Check, ConstraintKind::ForeignKey]`.

That is the only edit those three files get in this spec.

### 2.6 Reading them on PostgreSQL

In `src/connectors/postgres.rs`, the existing `CONSTRAINT_QUERY` filters
`con.contype IN ('p', 'u', 'c')`. Add `'f'`, and add the columns a foreign key
needs: the referenced table, the referenced columns in key order, and the two
action characters.

The referenced side comes from `con.confrelid` and `con.confkey`. `confkey` is
an array of attribute numbers in the *referenced* table, in the order that pairs
with `conkey`, so it needs the same `unnest ... WITH ORDINALITY` treatment the
local columns already get — not a plain join, which would return them in
whatever order the planner likes and silently pair the wrong columns together.

Qualify the referenced table with its schema, from `pg_namespace` joined through
`pg_class` on `confrelid`.

`confdeltype` and `confupdtype` are the internal `"char"` type, the same problem
`contype` already has. Cast them with `::text` in the query for the same reason
the existing comment gives.

| Character | `ReferentialAction` |
| --- | --- |
| `a` | `NoAction` |
| `r` | `Restrict` |
| `c` | `Cascade` |
| `n` | `SetNull` |
| `d` | `SetDefault` |
| anything else | `Other(the character as given)` |

Leave the existing rows for `p`, `u` and `c` alone. The `check_expr` column is
null for a foreign key, and the local-columns array already works for one.

**Update the comment that says foreign keys are deliberately absent.** It is
about to be false. There are two of them: one in `catalog.rs` above
`Constraint`, one above `CONSTRAINT_QUERY`.

## 3. Non-goals

- **No `CREATE`/`DROP` DDL for foreign keys anywhere.** This is a reporting
  change. Generating that DDL means ordering work across tables and is not part
  of this release.
- **Do not follow the reference.** The referenced table is recorded as a name.
  Nothing connects to it, reads its catalog, or checks that it exists.
- **Do not add `MATCH FULL`/`MATCH PARTIAL`, deferrability, or `NOT VALID`.**
  If PostgreSQL reports a key as `NOT VALID`, that is out of scope for this
  spec — but say so in your report if you notice the query returning them
  indistinguishably from valid ones.
- **Do not touch `src/data.rs`, `src/cli.rs`, `tauri-app/`, or the policy code
  in `src/schema.rs`.** Policy support for the new kind is 0.9c.
- **No new dependencies.**

## 4. Tests

### Unit tests, `src/catalog.rs`

| Test name | Must assert |
| --- | --- |
| `two_foreign_keys_onto_the_same_column_are_the_same_key_whatever_they_are_called` | Two `ForeignKey`s identical but for `name` produce no change |
| `a_key_that_cascades_is_not_the_same_key_as_one_that_restricts` | Same columns and referenced table, different `on_delete`, compares as one missing and one extra |
| `the_referenced_columns_pair_positionally_with_the_local_ones` | `(a, b) -> t(x, y)` and `(a, b) -> t(y, x)` are different keys |
| `a_referential_action_the_engine_reports_and_this_does_not_recognise_is_kept_verbatim` | `Other("SOMETHING")` renders as `SOMETHING` and is not equal to `NoAction` |
| `a_foreign_key_the_target_no_longer_enforces_is_breaking` | `ConstraintMissing` with a `ForeignKey` has `is_breaking() == true` |
| `a_foreign_key_displays_the_side_it_points_at` | `Display` contains `REFERENCES` and both column lists |
| `no_action_is_left_off_the_rendered_definition` | A key with both actions `NoAction` renders without `ON DELETE`/`ON UPDATE` |
| `a_connector_that_cannot_read_foreign_keys_reports_them_unread_not_absent` | A `TableCatalog` with `ForeignKey` in `unread` and none in `constraints`, compared against one that has a foreign key, produces **no** `ConstraintMissing` — and `unread_constraints()` names the kind |

That last one is the point of the whole spec. Write it first.

### Live PostgreSQL tests, `tests/catalog_postgres.rs`

Follow the file's existing pattern: `#[ignore]`, fixture tables created and
dropped by the test.

| Test name | Must assert |
| --- | --- |
| `a_foreign_key_is_read_with_the_table_and_columns_it_points_at` | A single-column key is read with its referenced table schema-qualified |
| `a_composite_foreign_key_keeps_both_sides_in_key_order` | A two-column key onto a two-column unique constraint reports both sides in the declared order |
| `the_declared_referential_actions_are_read_rather_than_assumed` | `ON DELETE CASCADE ON UPDATE RESTRICT` comes back as `Cascade` and `Restrict`, and a key declared with neither comes back as `NoAction` for both |
| `a_foreign_key_does_not_appear_as_an_index` | The index backing the referenced unique constraint is still excluded, and the foreign key appears once in `constraints` and nowhere else |

### Show it working

Against a live PostgreSQL, create two tables that differ only in that the target
has dropped a foreign key, then run:

```bash
cargo run -- schema --source "$PG" --source-query fk_source --target "$PG" --target-query fk_target
```

Report the command and the section of output naming the key. Before this change
that output does not mention it at all.
