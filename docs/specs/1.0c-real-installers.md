# Spec: real installers instead of bare binaries

**Target release:** 1.0
**Repository:** `bijection` (free crate) — `.github/workflows/release.yml`
**Owner:** the lead, **not the local implementer.** This is CI work, it can only
be proven by pushing a tag, and the standing brief forbids editing `.github/`.
Written down so the plan is reviewable and survives the session.
**Depends on:** `check-portable` green (it is), and ideally 1.0a and 1.0b, so the
first app people install is the one that reports foreign keys properly.

---

## 1. The gap

Every release today ships a bare executable. A Windows user gets
`biject-gui.exe` with no Start menu entry. A macOS user gets a file called
`biject-gui` that Finder does not recognise as an application. A Linux user
outside Arch gets a binary and a list of WebKitGTK packages to install
themselves.

Nobody who is not already a developer gets past that, and the landing page is
aimed at people who are merely database-adjacent.

---

## 2. Two different problems, and only one is easy

### 2.1 The desktop app — easy

The app is Tauri 2, and `tauri.conf.json` is already configured for bundling:
`"bundle": { "active": true, "targets": "all" }`, with `icon.ico` and
`icon.icns` present. The workflow simply never asks for a bundle — it runs
`cargo build`, which produces the raw binary. Swapping that for `cargo tauri
build` produces, with no code changes:

| Platform | Output |
| --- | --- |
| Windows | `.msi` (WiX) and `-setup.exe` (NSIS) |
| macOS | `.app` inside a `.dmg` |
| Linux | `.deb`, `.rpm`, `.AppImage` |

Each is a double-click install with a Start menu or Applications entry. The
`.AppImage` also removes the WebKitGTK dependency list for Linux users, since it
carries its own.

### 2.2 The command-line tool — the harder part

Tauri's installers install the *app*. They do not put `biject` on anybody's
`PATH`, and the CLI is the half most users of this tool want. Getting a
command-line binary installed with one command is a per-platform package manager
job:

| Platform | Channel | Effort |
| --- | --- | --- |
| macOS, Linux | a Homebrew tap: a `vixinxiviir/homebrew-tap` repository holding one formula that points at the release tarball and its checksum | small, and updated per release by a CI step |
| Windows | Scoop: a bucket repository with one JSON manifest | small, same shape as the tap |
| Windows | winget: a manifest submitted to Microsoft's `winget-pkgs` repository | moderate — a PR per release, reviewed by Microsoft |
| Arch | the AUR | done |
| anywhere with Rust | `cargo install biject --locked` | done |

**Recommendation:** Homebrew tap and Scoop bucket for 1.0. Both are repositories
you own, so a release never waits on anyone else. winget after 1.0, when there
is a reason to be in the Microsoft Store's search results.

The paid binary is a separate question — see section 5.

## 3. What to build

### 3.1 Bundles in the workflow

In `mac-windows-artifacts` and `linux-artifacts`:

- Install the Tauri CLI with `taiki-e/install-action` (`tool: tauri-cli`), the
  same way `cargo-about` is installed, rather than `cargo install` on every run.
- Replace the desktop `cargo build` with `cargo tauri build`, run from
  `tauri-app/src-tauri`. On macOS pass `--target universal-apple-darwin`, which
  does the two-architecture build and the `lipo` merge that the current
  workflow does by hand, and removes that step.
- Upload `tauri-app/src-tauri/target/**/release/bundle/**` in place of the bare
  `biject-gui`.
- Keep shipping the bare CLI binary alongside, archived per platform —
  `biject-<version>-<platform>.tar.gz`, `.zip` on Windows. The package-manager
  formulas in 3.2 need a stable archive URL to point at.

The Linux job needs two extra packages for `.rpm` and `.AppImage` —
`rpm` and `file` — and the Tauri CLI downloads `linuxdeploy` itself. Check the
Tauri 2 prerequisites page at the time rather than this list.

### 3.2 A Homebrew tap and a Scoop bucket

Two new public repositories, each holding one generated file. A final workflow
job, after all artifact jobs, fills in the version and the SHA-256 of each
archive and pushes to both. That job needs a token with write access to those
two repositories, stored as a secret — never one with access to this repository
or to `biject-pro`.

Until that job exists, updating the two files by hand at release time is fine.
They are twenty lines each.

### 3.3 Update the README and the landing page

"Installation" leads with the one-line install per platform, and demotes source
builds to the end. The landing page's install section does the same.

## 4. Decide before building

**Signing.** An unsigned `.msi` gets a SmartScreen warning with a "Run anyway"
link. An unsigned `.dmg` gets Gatekeeper's "cannot be opened" dialog, which
most users do not know how to bypass. Installers make this *more* visible, not
less, because they are what a non-developer double-clicks.

Either sign — Apple Developer Program for macOS, a code-signing certificate for
Windows, both paid and recurring — or ship unsigned and put the bypass steps
beside the download link. The second is a legitimate 1.0 answer. Leaving people
to meet the dialog cold is not.

Homebrew sidesteps most of this for the CLI: a formula-installed binary is not
quarantined the way a browser download is.

---

## 5. The paid binary

`biject-pro` has no CI, so none of the above reaches it yet. The paid build
does not need the Tauri bundler — it is a CLI — but a buyer still wants
one-command installation. Options, in order of effort:

1. **A zip per platform** with the binary and a README saying where to put it.
   What the runbook describes today.
2. **A private Homebrew tap** the buyer adds with a token. Awkward, and a token
   in a buyer's hands is a token that leaks.
3. **A signed installer per platform** that also writes the licence to the
   config directory. The nicest experience, and the most work.

**Recommendation:** option 1 for 1.0, done well — one archive per platform, a
checksum, and install instructions a non-developer can follow. It requires CI
in `biject-pro` for the macOS build, which is the real blocker.

---

## 6. Acceptance

A `v1.0.0-rc.N` tag produces, on the GitHub release:

- a `.msi` and `-setup.exe` that install on a clean Windows machine and put
  Bijection in the Start menu;
- a `.dmg` whose `.app` launches from Applications on both Apple Silicon and
  Intel;
- a `.deb`, `.rpm` and `.AppImage`, of which at least the `.AppImage` has been
  run on a machine without WebKitGTK installed;
- per-platform CLI archives with checksums;

and `brew install vixinxiviir/tap/biject` and `scoop install biject` each give a
working `biject --version`.

**Size:** the bundles are an afternoon. The tap and bucket are an afternoon.
Signing, if chosen, is mostly waiting on Apple and a certificate authority.
