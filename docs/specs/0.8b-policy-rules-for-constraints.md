# Spec: policy rules for constraints and indexes

**Target release:** 0.8
**Repository:** `bijection` (free crate)
**Depends on:** nothing. Can be done at any time, in any order.
**Size:** four fields on a struct, four checks in one function, tests

---

## 1. The gap

`biject schema --policy rules.json` asserts a schema against written rules and
exits non-zero when they are broken. It is the CI gate.

The policy understands columns and types and nothing else:

```rust
struct SchemaPolicy {
    required_columns_source: Option<Vec<String>>,
    required_columns_target: Option<Vec<String>>,
    forbidden_removals: Option<Vec<String>>,
    max_new_columns: Option<usize>,
    allowed_type_changes: Option<Vec<AllowedTypeChange>>,
    fail_on_breaking: Option<bool>,
}
```

0.6 taught the comparison to read primary keys, unique constraints, check
constraints and indexes. The policy never caught up. So today you cannot write
the rule a team most obviously wants — *this table must keep its primary key* —
even though the tool can see the primary key perfectly well.

`fail_on_breaking` does catch a dropped key, because losing a rule the source
enforces is classified as breaking and the compatibility summary feeds the
policy. But that is all-or-nothing: it fails on every breaking change at once
and cannot express "I do not care about column removals here, but the unique
index on `email` is not negotiable."

---

## 2. What to build

### 2.1 Four new policy fields

All optional, all absent-means-unchecked, matching the existing style:

```rust
/// Constraint kinds that must not be lost. Naming a kind here fails the
/// policy if the source enforces one and the target does not.
require_constraints: Option<Vec<String>>,

/// Columns that must be covered by a primary key on both sides.
require_primary_key_on: Option<Vec<String>>,

/// Index or constraint names that must exist on the target.
require_indexes: Option<Vec<String>>,

/// Fail if the target enforces a rule the source does not.
forbid_extra_constraints: Option<bool>,
```

`require_constraints` takes the same words `ConstraintKind` serialises as:
`primary_key`, `unique`, `check`, `index`. An unknown word is an error in the
policy file, not a silently ignored rule — see §2.4.

### 2.2 `evaluate_policy` needs the metadata

It currently receives `added`, `removed`, `type_changes` and `compatibility`. Add
the metadata changes and both catalogs — it needs the catalogs for
`require_primary_key_on` and `require_indexes`, which are questions about what
the schema *is*, not about what changed.

Pass `&MetadataReport`. It carries `changes` plus both `CatalogAvailability`
values, so one parameter covers all four rules.

### 2.3 The four checks

**`require_constraints`** — for each named kind, if `metadata.changes` contains a
`ConstraintMissing` whose constraint is of that kind, or an `IndexMissing` when
the kind is `index`, record a violation:

```
policy requires unique constraints to be preserved, but UNIQUE (email) is missing from target
```

**`require_primary_key_on`** — read the target catalog's `primary_key()`. Violation
if there is no primary key, or if its columns are not exactly the listed columns
in the listed order:

```
policy requires a primary key on (tenant_id, id), but target has PRIMARY KEY (id)
```

```
policy requires a primary key on (id), but target has no primary key
```

Order matters and the message must show both sides — a composite key in the
wrong order is a real difference and an easy thing to misread.

**`require_indexes`** — for each name, violation if no index in the target catalog
and no constraint in the target catalog carries that name:

```
policy requires an index named orders_customer_idx, and target has none
```

Match on name here, unlike everywhere else in this project, and **say so in a
comment**: comparison matches constraints by what they do because engine-generated
names differ, but a policy file is written by a person naming a thing they know
exists. Matching their string against a generated name would make the rule
unwritable.

Look in both `indexes` and `constraints`: on MySQL a `CREATE UNIQUE INDEX`
arrives as a unique constraint, on PostgreSQL as an index, and a policy author
should not have to know which.

**`forbid_extra_constraints`** — when true, any `ConstraintExtra` or `IndexExtra`
is a violation:

```
policy forbids constraints the source does not have, but target has UNIQUE (legacy_code)
```

### 2.4 Two ways to be honest about what was not checked

Both matter more than the rules themselves.

**An unreadable catalog must not pass silently.** `require_primary_key_on` and
`require_indexes` read the target catalog. If it is not `Available` — a CSV, a
`SELECT`, a failed lookup — the rule cannot be evaluated. Record a violation
saying so rather than passing:

```
policy requires a primary key on (id), but the target's catalog could not be read: file sources have no catalog to read
```

A rule that quietly does not run is worse than no rule, because CI goes green
and everyone believes it was checked.

**An unreadable constraint kind must not pass silently either.** If
`require_constraints` names `check` and either catalog lists `check` in its
`unread`, the comparison never looked. Same treatment:

```
policy requires check constraints to be preserved, but they could not be read from the source: SQLite keeps check constraints only in the original CREATE TABLE text
```

Use `CatalogAvailability::explain()` and `ConstraintKind`'s `Display` for the
wording rather than writing new strings.

**An unknown constraint kind is a policy error.** `load_policy` must reject a
`require_constraints` entry that is not one of the four kinds, with a message
naming the bad value and listing the valid ones. A typo like `uniqe` silently
matching nothing is the same silent-pass failure.

## 3. Non-goals

- **No new command-line flags.** This is the policy file only.
- **No change to `fail_on_breaking`.** It keeps working as it does.
- **No foreign keys.** They are not modelled anywhere in this project.
- **Do not touch `src/connectors/`.**
- **No new dependencies.**

## 5. Tests

In `src/schema.rs`'s existing test module. Build `SchemaDiffResult` values with
the helpers already there.

| Test name | Must assert |
| --- | --- |
| `a_policy_can_require_a_primary_key_to_survive` | Source has a primary key, target does not, `require_constraints: ["primary_key"]` produces one violation naming the key |
| `a_required_primary_key_must_be_on_the_named_columns` | Target has `PRIMARY KEY (id)`, policy requires `["tenant_id", "id"]`, violation shows both what was required and what was found |
| `primary_key_column_order_is_part_of_the_requirement` | Target key `(id, tenant_id)` against a requirement of `(tenant_id, id)` is a violation. Comment: a composite key in the wrong order serves different queries |
| `a_named_index_may_be_required_by_name` | `require_indexes: ["orders_customer_idx"]` passes when the target has it, fails when it does not |
| `a_required_index_is_found_whether_the_engine_calls_it_a_constraint_or_an_index` | The same name satisfies the rule when it appears in `constraints` and when it appears in `indexes`. Comment: MySQL reports `CREATE UNIQUE INDEX` as a constraint, PostgreSQL as an index |
| `extra_constraints_can_be_forbidden` | `forbid_extra_constraints: true` with a `ConstraintExtra` present is a violation; with none, it passes |
| `a_rule_that_could_not_be_evaluated_fails_rather_than_passes` | Target catalog is `NotADatabase`, `require_primary_key_on` set: exactly one violation, and its text contains the reason from `explain()`. Comment: a rule that quietly does not run is worse than no rule |
| `a_constraint_kind_the_source_could_not_read_is_not_reported_as_satisfied` | Source catalog lists `check` in `unread`, `require_constraints: ["check"]`: a violation saying it could not be read |
| `an_unknown_constraint_kind_is_rejected_when_the_policy_loads` | A policy naming `uniqe` fails to load, and the error names the bad value and lists the valid ones |
| `a_policy_with_none_of_the_new_fields_behaves_exactly_as_before` | An existing policy JSON with only the old fields produces the same result it did before this change |

That last one is the regression guard: these fields are optional and nobody's
existing policy file may change meaning.
