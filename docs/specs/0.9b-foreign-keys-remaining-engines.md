# Spec: foreign keys — MySQL, SQL Server and SQLite

**Target release:** 0.9
**Repository:** `bijection` (free crate)
**Depends on:** 0.9a. The `ForeignKey` variant and `ReferentialAction` must
exist before this can compile.
**Size:** three catalog queries in three connectors. Larger than 0.9a and the
most error-prone spec in the 0.9 queue, because each engine reports a foreign
key one *column* at a time and the grouping is where the bugs live.

---

## 1. The gap

After 0.9a, PostgreSQL reads foreign keys and the other three connectors declare
`ConstraintKind::ForeignKey` unread. That is honest but unhelpful: three of the
four supported engines now print "foreign keys were not compared" on every run.

This spec makes each of them read one, and removes the `unread` declaration as
it does — **only** for the engine that gains reading, and only in the same
change.

---

## 2. The shape of the problem, before the SQL

All three engines return **one row per key column**, not one row per key. A
two-column foreign key is two rows sharing a constraint name. So each connector
has to group rows into keys, and the ordering has to survive the grouping:

- Order by the constraint's identity first, then by the column's position within
  the key. Do not rely on the server returning rows grouped, and do not sort by
  column name — key order is not alphabetical order, and a wrongly ordered pair
  is a wrong answer that looks right.
- The local column at position *n* pairs with the referenced column at position
  *n*. Both lists come from the same rows, so if the ordering is right for one
  it is right for the other.

Write the grouping once per connector, in that connector, in whatever style the
file already uses for its constraint reading. Do not add a shared helper module.

## 3. MySQL — `src/connectors/mysql.rs`

Two `information_schema` views are needed. `KEY_COLUMN_USAGE` has the columns
but not the actions; `REFERENTIAL_CONSTRAINTS` has the actions but not the
columns.

```sql
SELECT kcu.CONSTRAINT_NAME,
       kcu.COLUMN_NAME,
       kcu.REFERENCED_TABLE_NAME,
       kcu.REFERENCED_COLUMN_NAME,
       rc.DELETE_RULE,
       rc.UPDATE_RULE
FROM information_schema.KEY_COLUMN_USAGE kcu
JOIN information_schema.REFERENTIAL_CONSTRAINTS rc
  ON  rc.CONSTRAINT_SCHEMA = kcu.CONSTRAINT_SCHEMA
  AND rc.CONSTRAINT_NAME   = kcu.CONSTRAINT_NAME
  AND rc.TABLE_NAME        = kcu.TABLE_NAME
WHERE kcu.TABLE_SCHEMA = ?
  AND kcu.TABLE_NAME   = ?
  AND kcu.REFERENCED_TABLE_NAME IS NOT NULL
ORDER BY kcu.CONSTRAINT_NAME, kcu.ORDINAL_POSITION
```

The `REFERENCED_TABLE_NAME IS NOT NULL` filter is load-bearing:
`KEY_COLUMN_USAGE` also holds every primary key and unique constraint, and
without it every one of them becomes a foreign key with no target.

`referenced_table` is `REFERENCED_TABLE_NAME` alone. MySQL's schema *is* its
database, so the connector is already scoped to one and qualifying would add a
name the user did not write.

Actions arrive as text:

| `DELETE_RULE` / `UPDATE_RULE` | `ReferentialAction` |
| --- | --- |
| `NO ACTION` | `NoAction` |
| `RESTRICT` | `Restrict` |
| `CASCADE` | `Cascade` |
| `SET NULL` | `SetNull` |
| `SET DEFAULT` | `SetDefault` |
| anything else | `Other(the text as given)` |

Match case-insensitively on the trimmed text.

**One thing to check against a real server rather than take from this spec.**
InnoDB is documented as treating `NO ACTION` and `RESTRICT` identically, and may
report one where the other was declared. Create a key with each, read them back,
and **report what you actually saw.** Do not write code that "corrects" one into
the other either way — if the server collapses them, that is a fact about MySQL
worth a comment in the code, not something to undo.

This connector's `unread` list is built conditionally — check constraints are
pushed when their query fails, indexes when theirs does. Follow that pattern: if
the foreign key query fails, push `ConstraintKind::ForeignKey` rather than
returning an error, because a table whose other metadata read fine is still
worth reporting on. Remove the unconditional push added in 0.9a.

## 4. SQL Server — `src/connectors/sqlserver.rs`

`sys.foreign_keys` and `sys.foreign_key_columns`, joined to `sys.columns` twice
because the two sides live in different tables.

```sql
SELECT fk.name,
       OBJECT_SCHEMA_NAME(fk.referenced_object_id) + '.' + OBJECT_NAME(fk.referenced_object_id),
       pc.name,
       rc.name,
       fk.delete_referential_action_desc,
       fk.update_referential_action_desc
FROM sys.foreign_keys fk
JOIN sys.foreign_key_columns fkc
  ON fkc.constraint_object_id = fk.object_id
JOIN sys.columns pc
  ON pc.object_id = fkc.parent_object_id AND pc.column_id = fkc.parent_column_id
JOIN sys.columns rc
  ON rc.object_id = fkc.referenced_object_id AND rc.column_id = fkc.referenced_column_id
WHERE fk.parent_object_id = OBJECT_ID(@P1)
ORDER BY fk.name, fkc.constraint_column_id
```

Pass the schema-qualified table name to `OBJECT_ID` the same way the existing
queries in this file identify their table. Match their parameter style.

`referenced_table` is schema-qualified, matching what PostgreSQL produces and
what SQL Server itself prints.

Actions arrive as text with **underscores**, and SQL Server has no `RESTRICT`:

| `*_referential_action_desc` | `ReferentialAction` |
| --- | --- |
| `NO_ACTION` | `NoAction` |
| `CASCADE` | `Cascade` |
| `SET_NULL` | `SetNull` |
| `SET_DEFAULT` | `SetDefault` |
| anything else | `Other(the text as given)` |

Note the underscores in your code with a one-line comment. Somebody will later
copy the MySQL mapping over this one and every action will silently become
`Other`.

## 5. SQLite — `src/connectors/sqlite.rs`

`PRAGMA foreign_key_list('table')`, whose columns are
`id, seq, table, from, to, on_update, on_delete, match`.

Three things about it are unlike the other engines.

**There is no constraint name.** SQLite does not keep one. Synthesise
`foreign_key_<id>` from the pragma's `id` column. This is safe because
`Constraint::identity` excludes names by design, so a synthesised name never
causes or hides a difference — it only gives the report something to print.

**Group by `id`, order by `seq`.** `id` identifies the key, `seq` is the column
position within it. Both are integers, and `seq` is 0-based.

**`to` is NULL when the key was declared without a column list.**
`REFERENCES customers` — no parenthesised columns — means "the referenced
table's primary key", and the pragma reports that as a null rather than naming
the columns. **This is the input this spec most needs you to get right.**

Resolve it: run `PRAGMA table_info('<referenced table>')` and take the columns
with a non-zero `pk` value, ordered by that `pk` value, which is the position in
the key rather than a boolean.

If that resolution does not work — the referenced table is not in this database,
the pragma fails, or the referenced table has no primary key — then the key's
referenced columns are genuinely unknown. In that case:

- do not record the key with an empty or guessed column list, and
- push `ConstraintKind::ForeignKey` onto this table's `unread` list.

That makes the whole kind skipped for this table rather than half-reported. A
foreign key recorded with no referenced columns would compare unequal to the
identical key on the other side, and the report would name a difference that
does not exist.

Reading the referenced table's pragma is a deliberate exception to 0.9a's "do
not follow the reference". It applies only here and only because SQLite offers
no other way to learn what the key points at. Say so in a comment.

Actions arrive as text in the same vocabulary MySQL uses (`NO ACTION`,
`RESTRICT`, `CASCADE`, `SET NULL`, `SET DEFAULT`); map them the same way, with
`Other` for anything else.

`referenced_table` is the bare name the pragma gives. SQLite has no schemas.

Remove `ConstraintKind::ForeignKey` from the `with_unread` call added in 0.9a.
**Leave `ConstraintKind::Check` in it** — check constraints are still unread on
SQLite and that is unchanged by this spec.

### Worth a doc comment, not a model change

SQLite does not enforce foreign keys unless `PRAGMA foreign_keys = ON` is set,
per connection. So a SQLite table can declare a key that the database is not
checking. That is a property of whoever connects, not of the schema, so there is
nothing here to compare — but a note in the connector saves the next person
working out why a declared key did not prevent anything.

## 6. Non-goals

- **No DDL generation**, on any engine.
- **Do not change `src/catalog.rs`.** If you find you need to, the model from
  0.9a is wrong and that is worth stopping to say rather than working around.
- **Do not touch `src/schema.rs`, `src/cli.rs`, `src/data.rs` or `tauri-app/`.**
- **Do not refactor the three connectors' constraint reading into a shared
  helper.** They read three different catalogs with three different client
  libraries; the shared part is smaller than it looks.
- **No new dependencies.**

## 7. Tests

Each connector's existing test module covers whatever it can without a server —
usually the parsing and grouping. Put the grouping logic somewhere a unit test
can reach it, as the file already does for its other catalog work, and cover:

| Test name | Must assert |
| --- | --- |
| `a_composite_key_is_one_constraint_rather_than_one_per_column` | Two rows sharing a name become a single `ForeignKey` with two columns |
| `key_order_follows_the_declared_position_not_the_column_name` | Rows whose position order and alphabetical order disagree produce the declared order |
| `two_keys_on_one_table_do_not_merge` | Rows for two different constraint names produce two constraints |
| `an_action_the_engine_spells_differently_is_kept_verbatim` | An unrecognised action string becomes `Other` with that string |

SQLite additionally:

| Test name | Must assert |
| --- | --- |
| `a_key_declared_without_a_column_list_resolves_to_the_referenced_primary_key` | A live SQLite database with `REFERENCES parent` reports the parent's primary key columns |
| `a_composite_primary_key_resolves_in_key_order` | Resolution orders by the pragma's `pk` value, not by column order in the table |
| `a_key_whose_target_cannot_be_read_leaves_the_kind_unread` | Foreign keys end up in `unread` and no partial key is recorded |

SQLite tests can run without a server — the existing tests in that file build a
real database in a temporary file. Use the same helper.

For MySQL and SQL Server, if the repository has no live test harness for them,
say so in your report and note which behaviour is therefore unverified. Do not
claim a query works because it compiles; **every connector defect this project
has found was invisible to a passing test suite**, and three of them were in
exactly this kind of catalog query.

### Show it working on SQLite

Build one database with two tables that differ only in a foreign key, and run:

```bash
cargo run -- schema --source sqlite://fk.sqlite --source-query with_fk --target sqlite://fk.sqlite --target-query without_fk
```

Report the output. It must name the key and must **not** say foreign keys were
unread.
