# Spec: rendering a canonical type — dates, binary, structured

**Target release:** 0.7
**Repository:** `bijection` (free crate)
**Depends on:** `0.7b-render-common-types`. That spec built `Dialect::render_type`
and `UnsupportedType`; this one extends the same function.
**Size:** more arms on an existing match, plus tests

Read 0.7b first. Its §2.1 rule governs this spec too, and this is where that
rule does most of its work — a majority of the entries below are refusals.

---

## 1. Why this half is separate

The types in 0.7b exist almost everywhere and differ only in name. The ones here
do not. PostgreSQL has `interval`, `jsonb` and a real `uuid`; MySQL has none of
those. SQL Server has `datetimeoffset`; PostgreSQL calls the same idea
`timestamptz`; MySQL has nothing equivalent that is safe to use.

That makes this the part where the temptation to substitute is strongest, and
where substituting does the most damage — a timestamp written into the wrong
type loses a time zone or overflows in 2038, and nothing tells you until it does.

---

## 2. The rendering table

Same conventions as 0.7b: `{n}` is the first parameter, `MAX` means
`sqltype::UNBOUNDED`, "refuse" means `Err(UnsupportedType)`.

### Dates and times

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `date` | `date` | `date` | `date` | `date` |
| `time` | `time` | `time` | `time` | `time` |
| `timetz` | `timetz` | refuse | refuse | `timetz` |
| `timestamp` | `timestamp` | `datetime` | `datetime2` | `timestamp` |
| `timestamptz` | `timestamptz` | refuse | `datetimeoffset` | `timestamptz` |
| `interval` | `interval` | refuse | refuse | `interval` |

Four of these need their reasoning in comments, because each one looks like an
oversight to a reader who has not thought it through:

- **`timestamp` on MySQL is `datetime`, not `TIMESTAMP`.** MySQL's `TIMESTAMP`
  converts to and from UTC using the session time zone and cannot hold a value
  past 2038. `DATETIME` is the type that stores what it was given, which is what
  a timestamp without a time zone means everywhere else.
- **`timestamp` on SQL Server is `datetime2`, not `datetime`.** SQL Server's
  `timestamp` is not a date at all — it is a row-version counter, an entirely
  unrelated type, and writing it would produce a column that cannot hold a date.
  `datetime` is the older type with a ~3ms resolution and a 1753 lower bound;
  `datetime2` is the supported one.
- **`timestamptz` is refused on MySQL.** The nearest thing is `TIMESTAMP`, which
  brings the 2038 limit and session-dependent conversion described above. There
  is no MySQL type that stores an instant faithfully, so there is nothing honest
  to write.
- **`timetz` is refused on MySQL and SQL Server.** Neither has a time-of-day type
  carrying a zone. SQL Server's `datetimeoffset` carries a date as well, so it is
  a different type, not a rename.

### Binary

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `bytea` | `bytea` | `longblob` | `varbinary(max)` | `blob` |
| `varbinary` with `{n}` | refuse | `varbinary({n})` | `varbinary({n})` | `varbinary({n})` |
| `varbinary` with `MAX` | `bytea` | `longblob` | `varbinary(max)` | `blob` |
| `binary` with `{n}` | refuse | `binary({n})` | `binary({n})` | `binary({n})` |

- **`varbinary({n})` and `binary({n})` are refused on PostgreSQL.** `bytea` is
  unbounded and has no length or fixed-width form, so rendering it would drop a
  constraint the source declared. Unbounded `varbinary` *is* `bytea` and renders
  normally, because nothing is lost.

### Structured and identifier types

| Canonical | PostgreSQL | MySQL | SQL Server | SQLite |
| --- | --- | --- | --- | --- |
| `uuid` | `uuid` | refuse | `uniqueidentifier` | `uuid` |
| `json` | `json` | `json` | refuse | `json` |
| `jsonb` | `jsonb` | refuse | refuse | refuse |
| `xml` | `xml` | refuse | `xml` | refuse |

- **`uuid` is refused on MySQL.** MySQL has no UUID type. Real schemas use
  `CHAR(36)` or `BINARY(16)`, and those are different types with different
  storage and different comparison behaviour — a choice for a person to make,
  not for this code.
- **`json` is refused on SQL Server.** SQL Server validates JSON with a check
  constraint on an `nvarchar(max)` column rather than providing a type. Writing
  `nvarchar(max)` would silently drop the validation.
- **`jsonb` is PostgreSQL only.** It is a storage format, not just a name.

### SQLite, once more

SQLite renders the canonical name for everything above except `bytea`, which
becomes `blob` — SQLite's own name for the same thing, and the only one with
blob affinity. SQLite applies type affinity to whatever text is declared and
stores that text verbatim, so writing the canonical name is what a SQLite user
would have written.

## 3. Non-goals

- **Do not revisit 0.7b's types.** If a test from 0.7b changes behaviour, the
  implementation is wrong.
- **No DDL, no column definitions, no statements.**
- **No changes outside `src/sqldialect.rs`.**
- **No new dependencies.**

## 4. Tests

Add to the same test module 0.7b created.

| Test name | Must assert |
| --- | --- |
| `a_timestamp_without_a_zone_avoids_the_types_that_are_not_one` | `timestamp` renders `datetime` on MySQL and `datetime2` on SQL Server. Assert explicitly that the SQL Server rendering is **not** `timestamp` and **not** `datetime`. Comment: SQL Server's `timestamp` is a row-version counter, not a date |
| `mysql_gets_no_timestamp_with_a_time_zone` | `timestamptz` on MySQL is `Err`. Comment: MySQL's `TIMESTAMP` converts through the session zone and stops in 2038, so there is nothing faithful to write |
| `an_instant_uses_each_engines_own_type_where_it_has_one` | `timestamptz` renders `timestamptz` on PostgreSQL and `datetimeoffset` on SQL Server |
| `a_zoned_time_of_day_is_refused_where_it_does_not_exist` | `timetz` is `Ok` on PostgreSQL and SQLite, `Err` on MySQL and SQL Server |
| `an_interval_is_postgres_only` | `interval` is `Ok` on PostgreSQL and SQLite, `Err` on MySQL and SQL Server |
| `unbounded_binary_maps_cleanly_but_bounded_binary_does_not` | `varbinary(max)` renders `bytea` on PostgreSQL; `varbinary(50)` on PostgreSQL is `Err`. Comment: `bytea` has no length, so a bounded rendering would drop a declared constraint |
| `binary_types_use_each_engines_own_name` | `bytea` renders `longblob` on MySQL, `varbinary(max)` on SQL Server, `blob` on SQLite |
| `a_uuid_is_not_turned_into_a_string` | `uuid` on MySQL is `Err`, and the error text mentions neither `char` nor `binary`. Comment: `CHAR(36)` and `BINARY(16)` are both real choices and both are a person's call |
| `json_is_refused_where_it_is_a_convention_rather_than_a_type` | `json` on SQL Server is `Err`; `jsonb` is `Ok` only on PostgreSQL |
| `sqlite_takes_the_canonical_name_for_everything_but_blobs` | `interval`, `uuid`, `timetz` all render their canonical names on SQLite; `bytea` renders `blob` |

Only `src/sqldialect.rs` may appear.

After this spec, every canonical base in `src/sqltype.rs`'s alias table has a
decision recorded for all four dialects — a rendering or a refusal, with no base
falling through to a generic "not supported by this version". Check that by
reading the two tables against `sqltype::lookup_base` and say in your report if
any base is unaccounted for.
