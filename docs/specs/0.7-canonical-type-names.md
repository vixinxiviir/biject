# Spec: canonical type names

**Target release:** 0.7
**Repository:** `bijection` (the free, GPL-3.0-only crate). Do not touch `biject-pro`.
**Estimated size:** one new module, three small edits to `src/catalog.rs`, one new test file section.

---

## 1. The defect

A schema comparison reports two columns as having a **breaking type change** when
they hold the same type spelled a different way.

Reproduce it. This needs no database server — SQLite stores a declared type
verbatim, which makes it the cheapest way to see the bug:

```bash
python -c "
import sqlite3, os
p = 'alias.sqlite'
if os.path.exists(p): os.remove(p)
c = sqlite3.connect(p)
c.executescript('''
CREATE TABLE a (id INT, amount DECIMAL(12,2), name VARCHAR(50));
CREATE TABLE b (id INTEGER, amount NUMERIC(12,2), name CHARACTER VARYING(50));
''')
"
```

```bash
cargo run -- schema --source sqlite://alias.sqlite --source-query a --target sqlite://alias.sqlite --target-query b
```

Current output:

```
Schema metadata changes (3):
  - amount: DECIMAL(12,2) -> NUMERIC(12,2) [breaking]
  - id: INT -> INTEGER [breaking]
  - name: VARCHAR(50) -> CHARACTER VARYING(50) [breaking]
```

All three pairs are the same type. `DECIMAL` and `NUMERIC` are synonyms.
`INT` and `INTEGER` are synonyms. `VARCHAR(n)` and `CHARACTER VARYING(n)` are
synonyms — and that last one matters most, because **PostgreSQL's catalog always
reports the `character varying` spelling** while MySQL, SQL Server and most
hand-written DDL use `varchar`. So today, comparing a PostgreSQL table against a
table on any other engine reports a false breaking change on *every string
column*, and the compatibility verdict comes back `backward compatible: false`
for a schema that did not change.

After this change, those three rows must not appear at all — not "appear as
safe", but not be reported, because nothing changed.

## 2. What to build

A new module `src/sqltype.rs` that turns a declared type string into a canonical
form, plus three edits wiring it into the existing comparison.

### 2.1 The public API

```rust
/// A declared type reduced to a comparable form.
pub struct CanonicalType {
    /// The canonical base name, lowercase. For a spelling in the alias table
    /// this is the canonical member; otherwise it is the cleaned input.
    pub base: String,
    /// Size or precision parameters, in the order written.
    pub params: Vec<u64>,
    /// Whether `base` came from the alias table.
    pub recognised: bool,
}

/// Reduce a declared type to its canonical form.
pub fn canonical(declared: &str) -> CanonicalType;
```

`CanonicalType` derives `Debug, Clone, PartialEq, Eq`.

Move the existing `UNBOUNDED` constant (`u64::MAX`, the sentinel for SQL
Server's `varchar(max)`) into this module and make it `pub`.

### 2.2 Parsing rules, in order

1. Trim, lowercase, and collapse every run of whitespace to a single space.
   `"  CHARACTER   VARYING (50) "` becomes `"character varying (50)"`.
2. Split on the first `(` and the last `)`. Text before the `(` is the base;
   text between is the parameter list. Trim the base afterwards.
3. Parse each comma-separated parameter: `max` becomes `UNBOUNDED`; otherwise
   parse as `u64`. **If any parameter fails to parse, discard the whole
   parameter list** and return an empty `params`. This preserves today's
   behaviour for things like `enum('a','b')`, where the contents are values
   rather than sizes and comparing them numerically would be meaningless.
4. Look the base up in the alias table (§3). A hit sets `base` to the canonical
   member and `recognised = true`. A miss leaves `base` as the cleaned text and
   sets `recognised = false`.
5. **If the canonical base is an integer type, discard the parameters.** MySQL
   writes `int(11)`, where `11` is a display width with no bearing on what the
   column can hold; treating it as capacity would make `int(11)` and `int`
   compare unequal. Integer bases are: `integer`, `bigint`, `smallint`,
   `tinyint`, `mediumint`.

### 2.3 An unrecognised type must behave exactly as it does today

If a base is not in the alias table, the comparison must be no worse than the
current one: same-spelling matches, different-spelling differs. Since `base`
holds the cleaned text in that case, derived equality gives this for free. Do
not invent a fallback that guesses at similarity.

## 3. The alias table

Each row lists a canonical name and every spelling that maps to it. Matching is
on the cleaned base text from step 1. Anything not listed here is unrecognised.

Keep this as a single table in the source, ordered as below, with a comment
saying it may be extended but that entries are only added when two spellings
mean the *same type on the same engine*, or are the same standard type under two
names.

### Integers — parameters discarded

| Canonical | Spellings |
| --- | --- |
| `integer` | `int`, `integer`, `int4` |
| `bigint` | `bigint`, `int8` |
| `smallint` | `smallint`, `int2` |
| `tinyint` | `tinyint` |
| `mediumint` | `mediumint` |

### Exact numerics

| Canonical | Spellings |
| --- | --- |
| `numeric` | `numeric`, `decimal`, `dec`, `fixed` |

### Approximate numerics

| Canonical | Spellings |
| --- | --- |
| `real` | `real`, `float4` |
| `double precision` | `double precision`, `double`, `float8` |

`float` is deliberately **not** aliased. In PostgreSQL `float(n)` is `real` or
`double precision` depending on `n`; in MySQL it is its own type. Mapping it
either way would be wrong somewhere, so it stays unrecognised.

### Character types

| Canonical | Spellings |
| --- | --- |
| `varchar` | `varchar`, `character varying` |
| `char` | `char`, `character` |
| `nvarchar` | `nvarchar`, `national character varying` |
| `nchar` | `nchar`, `national character` |
| `text` | `text` |

`tinytext`, `mediumtext`, `longtext`, `ntext` and `clob` each stay unrecognised
and distinct. They hold different amounts and are not synonyms of `text`.

### Boolean

| Canonical | Spellings |
| --- | --- |
| `boolean` | `boolean`, `bool` |

### Date and time

| Canonical | Spellings |
| --- | --- |
| `timestamp` | `timestamp`, `timestamp without time zone` |
| `timestamptz` | `timestamptz`, `timestamp with time zone` |
| `time` | `time`, `time without time zone` |
| `timetz` | `timetz`, `time with time zone` |
| `date` | `date` |
| `interval` | `interval` |

`datetime`, `datetime2`, `smalldatetime` and `year` stay unrecognised. MySQL's
`DATETIME` and PostgreSQL's `TIMESTAMP` are arguably equivalent, but deciding
that is a cross-engine semantic judgement rather than a spelling one, and it is
out of scope here — see §5.

### Binary and other

| Canonical | Spellings |
| --- | --- |
| `bytea` | `bytea` |
| `varbinary` | `varbinary` |
| `binary` | `binary` |
| `uuid` | `uuid` |
| `json` | `json` |
| `jsonb` | `jsonb` |
| `xml` | `xml` |

Single-spelling rows are listed so the table doubles as the record of what has
been considered. They are `recognised = true` with no synonyms.

## 4. Wiring it in

Three edits in `src/catalog.rs`. Add `pub mod sqltype;` to `src/lib.rs`,
keeping the existing alphabetical order of the `pub mod` lines.

### 4.1 `compare()` — around line 573

Replace:

```rust
if normalize_type(&column.data_type) != normalize_type(&other.data_type) {
```

with a comparison of canonical forms. Delete `normalize_type` entirely once
nothing calls it.

**The reported text must stay the original declared text.** A real change still
reads `VARCHAR(50) -> VARCHAR(200)`, not `varchar(50) -> varchar(200)`. Only the
*decision* to report uses the canonical form.

### 4.2 `classify_type_change()` — around line 363

Replace the two `split_type` calls with `canonical`. The rest of the function is
unchanged: same base and same parameter count, then compare positionally; any
parameter smaller means `Narrowing`, all larger means `Widening`, otherwise
`Unknown`.

Delete `split_type` once nothing calls it, and remove the `UNBOUNDED` constant
from `catalog.rs` now that it lives in `sqltype.rs`.

This gains a behaviour worth having: `varchar(50) -> character varying(200)` now
classifies as `Widening`, where today it is `Unknown` and therefore breaking.

### 4.3 Doc comment on `TypeImpact`

The comment above `TypeImpact` says only same-family changes are classified and
that a per-dialect equivalence matrix is out of scope. That is still true, but it
now needs to say that spellings of the same type are folded together first.
Update it. Do not change the enum.

## 5. Non-goals — do not do these

- **No cross-engine semantic equivalence.** `datetime` stays distinct from
  `timestamp`, `tinyint(1)` stays distinct from `boolean`, `varchar` stays
  distinct from `text`. Those are judgement calls about what an engine *means*,
  not about how it *spells*. Anything in this class is deferred.
- **No DDL rendering.** Turning a `CanonicalType` back into per-dialect type text
  is the next spec, not this one.
- **No connector changes.** `src/connectors/*` is untouched. The types arrive as
  strings and this works on strings.
- **No new dependencies.** Everything here is `std`.
- **Do not edit** `CHANGELOG.md`, any `Cargo.toml` version, `README.md`, or
  anything under `.github/`. Those are handled at release.

## 6. Tests

Put unit tests in a `#[cfg(test)] mod tests` inside `src/sqltype.rs`, and the
comparison-level tests in the existing test module in `src/catalog.rs`.

Test names in this project are sentences describing the behaviour, not the
function under test. Each test carries a comment saying *why* the behaviour
matters when that is not obvious from the name. Follow the existing style.

### 6.1 In `src/sqltype.rs`

| Test name | Must assert |
| --- | --- |
| `the_same_type_spelled_differently_is_the_same_type` | `canonical("VARCHAR(50)") == canonical("character varying(50)")`; likewise `int`/`integer`, `decimal(12,2)`/`numeric(12,2)`, `bool`/`boolean`, `timestamp with time zone`/`timestamptz` |
| `case_and_whitespace_do_not_change_a_type` | `canonical("  CHARACTER   VARYING ( 50 ) ")` equals `canonical("varchar(50)")` |
| `an_integer_display_width_is_not_capacity` | `canonical("int(11)") == canonical("int")`, and its `params` is empty. Comment: MySQL writes a display width that says nothing about what the column holds |
| `size_is_kept_for_types_where_it_means_something` | `canonical("varchar(50)").params == vec![50]`; `canonical("numeric(12,2)").params == vec![12, 2]` |
| `max_is_an_unbounded_size` | `canonical("varchar(max)").params == vec![UNBOUNDED]` |
| `an_unparseable_parameter_list_is_discarded_rather_than_guessed_at` | `canonical("enum('a','b')").params` is empty and `base` is `enum`. Comment: those are values, not sizes |
| `an_unknown_type_keeps_its_own_name` | `canonical("geography").recognised == false` and `base == "geography"`; `canonical("geography") != canonical("geometry")` |
| `float_is_left_alone_because_its_width_depends_on_the_engine` | `canonical("float").recognised == false` |
| `types_that_are_not_synonyms_stay_distinct` | `canonical("text") != canonical("varchar(50)")`; `canonical("datetime") != canonical("timestamp")`; `canonical("tinyint") != canonical("boolean")` |

### 6.2 In `src/catalog.rs`

| Test name | Must assert |
| --- | --- |
| `a_type_spelled_differently_is_not_reported_as_a_change` | Build two catalogs whose only difference is `VARCHAR(50)` against `character varying(50)`, and assert `compare()` returns an empty vec. Comment: PostgreSQL's catalog reports the long spelling, so without this every string column differs on a cross-engine comparison |
| `a_real_type_change_still_reports_the_declared_text` | `varchar(50)` to `varchar(200)` produces one `NativeType` change whose `from` and `to` are the original strings, not canonicalised ones |
| `widening_is_recognised_across_spellings` | `classify_type_change("varchar(50)", "character varying(200)") == TypeImpact::Widening` |

### 6.3 Existing tests that must keep passing unchanged

Do not edit these. If one fails, the implementation is wrong, not the test.

- `classify_type_change("int", "bigint")` is `Unknown` — different canonical
  bases, so still unclassified.
- `classify_type_change("enum('a','b')", "enum('a','b','c')")` is `Unknown`.
- `classify_type_change("character varying(50)", "text")` is `Unknown`.
- Every widening/narrowing test around lines 820–900 of `src/catalog.rs`.

## 8. Notes on house style

- Comments explain **why**, not what. `// lowercase the base` is noise;
  `// PostgreSQL's catalog reports `character varying`, so a comparison against
  any other engine sees every string column as changed` is the kind that earns
  its place.
- No silent fallbacks. If something cannot be determined, the code says so
  through its return type rather than guessing. That is what `recognised` is
  for.
- Prefer being obviously right over being clever. This module is a lookup table
  and a string split; it should read like one.
